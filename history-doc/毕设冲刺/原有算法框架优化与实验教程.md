# 原有算法框架优化与实验教程

## 1. 文档定位

这份文档从主教程中提炼出前七步，只保留“原有 NoMaD 算法框架的优化与实验”部分。它的作用不是替代总教程，而是单独服务于论文第四章中与原始算法改进直接相关的内容。

这七步对应四类工作：

1. 环境与路径固化。
2. 数据一致性检查。
3. 原始 NoMaD 基线推理复现。
4. DDIM、CFG、TTS 与视觉编码器替换实验。

---

## 2. 目标产出

执行完这份文档后，应形成以下成果：

1. 一套可复现的训练/部署环境边界。
2. 一套可复核的数据与路径检查结果。
3. 一组原始 NoMaD 基线推理指标。
4. 一组 DDIM、CFG 与 TTS 的统计实验结论。
5. 一套视觉编码器升级的工作边界与阶段性结论。

## 3. 第一步：建立训练环境与部署环境边界

### 目标

把“训练环境”“仿真部署环境”“真机部署环境”彻底分开，避免后续把依赖问题误判成算法问题。

### 操作重点

1. 训练环境单独管理 `torch`、`diffusers`、`timm`、`wandb` 等依赖。
2. MuJoCo 仿真环境单独管理物理仿真与图形相关依赖。
3. 真机环境只保留运行 NoMaD 推理、桥接底层控制和采集图像所需依赖。

### 结论

这一步不是形式化准备，而是后续所有结果可信的前提。如果环境边界不清楚，训练结果、仿真结果和真机结果之间就无法建立严格的因果链。

### 实验设计分析

环境检查并不是为了“确认能启动”，而是为了确认实验所依赖的 Python、包版本、路径变量和 GPU 环境是否一致。只有环境一致，后续重复实验的均值、方差和置信区间才有意义。

### 结果维度分析

环境检查输出应重点确认以下几类信息：

1. Python 与关键依赖版本是否正确。
2. 是否能访问项目根路径与 `results/`。
3. 是否能找到训练配置、推理配置和默认权重路径。

### 结论

环境检查结果应作为整条证据链的第一张“合格证明”。这一步通过后，后续实验中的异常才值得归因到模型和算法，而不是环境缺陷。

3. 结论：统计意义上的最优部署加速配置是 `DDIM-2`，`DDIM-5` 可作为更保守备选。

## 8.3 TTS 推理时搜索实验

### 研究定位

这里的 `TTS` 不是语音合成中的 text-to-speech，而是 diffusion inference literature 中的 `test-time scaling / inference-time scaling`。  
它的核心思想不是改变训练目标，而是在推理阶段投入更多候选采样预算，再通过 verifier 选择更优轨迹。对于 NoMaD 而言，这一思路尤其适合放在 `DDIM / CFG` 之后，因为：

1. `DDIM` 决定单条轨迹如何去噪以及推理延迟。
2. `CFG` 决定单条轨迹的目标牵引强度。
3. `TTS` 决定在已经生成多条轨迹后，保留哪几条进入最终执行。

因此，TTS 不应被理解为“和 DDIM、CFG 并列相加的第三个开关”，而应被设计成推理组件中的外层候选选择机制。

### 代码入口

1. 快速验证：`scripts/experiments/tts_experiment.py`
2. 正式统计：`scripts/experiments/tts_stat_experiment.py`
3. 统一推理入口：`scripts/shared/nomad_inference.py`

### 组件设计原则

当前项目中，TTS 已经被设计成统一推理模块内的可选能力，主要参数包括：

1. `tts_enabled`
2. `tts_budget`
3. `tts_topk`
4. `tts_verifier`

其默认策略为 `best-of-N`：先采样 `tts_budget` 条轨迹，再根据 verifier 对其打分，保留前 `tts_topk` 条。  
当前 verifier 采用面向导航任务的启发式评分，而不是额外训练新的 value model，原因是这样更符合本项目当前工作量边界，也更容易与 NoMaD 的 waypoint 语义保持一致。

### 统计实验设计

为了让 TTS 不只停留在“可运行功能”，而成为可以写入论文第四章的正式实验，建议采用完整统计矩阵：

1. 基线：`ddpm_10 + cfg=0.0 + tts=0`
2. DDIM 单因素：`ddim_5`、`ddim_2`
3. CFG 单因素：`w=0.0`、`0.5`、`1.0`
4. TTS 单因素：`tts_budget=0`、`16`、`32`
5. 两两组合：
   `DDIM + CFG`、`DDIM + TTS`、`CFG + TTS`
6. 三者联合：
   `DDIM + CFG + TTS`

推荐使用下面这套正式统计命令：

```bash
python scripts/experiments/tts_stat_experiment.py \
  --cases-per-suite 8 \
  --num-runs 8 \
  --ddim-steps-list 5,2 \
  --cfg-weights 0.0,0.5,1.0 \
  --tts-budgets 0,16,32 \
  --tts-topk 4 \
  --tts-verifier heuristic
```

### 指标设计

TTS 统计实验建议至少保留以下指标：

1. `latency_ms`
2. `CI95(ms)`
3. `mse_vs_baseline`
4. `forward_progress_mean`
5. `lateral_abs_mean`
6. `smoothness_mean`
7. `verifier_score_mean`
8. `rank_score`

这里每个指标的意义如下：

1. `latency_ms`：启用 TTS 后的总推理延迟，直接反映推理预算代价。
2. `CI95(ms)`：延迟均值的 95% 置信区间半宽，用于判断统计稳定性。
3. `mse_vs_baseline`：相对原始 `ddpm_10 + cfg=0 + tts=0` 基线的轨迹偏移量。
4. `forward_progress_mean`：平均前向推进距离。
5. `lateral_abs_mean`：终点横向偏移绝对值均值。
6. `smoothness_mean`：轨迹二阶变化量，越小通常越平滑。
7. `verifier_score_mean`：TTS verifier 在保留轨迹上的平均打分。
8. `rank_score`：综合排序指标，用于从多种组合中选出候选最优部署配置。

### 当前研究结论

这一部分最终回答的不是“有没有加入 TTS”，而是下面三个更重要的问题：

1. TTS 是否能在相同模型下提升轨迹选择质量，而不是只徒增延迟。
2. DDIM 节省下来的推理预算，是否值得重新分配给 TTS。
3. CFG 与 TTS 是否存在过度叠加风险，即目标牵引过强后再被 verifier 偏好放大，导致轨迹变得更激进但不更稳定。

从当前实验结果看，结论不是“三个都开一定最好”，而是应给出更细分的部署结论：

1. 低延迟优先：`DDIM-2 + CFG=0.0 + TTS=0`
2. 当前默认推荐：`DDIM-2 + CFG=0.0 + TTS=8`
3. 复杂场景优先：`DDIM-2 + CFG=0.5/1.0 + TTS=8`
4. 保守质量优先：`DDIM-3/5 + CFG=0.0 + TTS=8/16`

因此，TTS 在论文中最适合被写成“推理时预算重分配与候选选择优化”，而不是单纯的新采样器。

## 10. 本文档对应的论文写法

这七步在论文中最适合被组织成三段：

1. 实验前准备：环境、路径、数据一致性。
2. 原始 NoMaD 优化：基线、DDIM、CFG、TTS。
3. 视觉编码器扩展：统一框架、离线潜力、闭环问题。

如果后续引用第五章的 MuJoCo 闭环结论，需要额外说明：

1. 原始算法统计优化支持 `DDIM-2` 作为主加速配置。
2. 更细粒度的闭环任务中，CFG 最优点会受到地图与编码器影响，最终应以 MuJoCo 闭环消融结果为准。
3. `TTS` 不宜被简单当成“额外开关”，而应和 `DDIM / CFG` 一起在统一推理层做组合搜索，并通过统计实验选出最终部署组合。
