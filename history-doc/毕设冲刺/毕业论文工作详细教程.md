> 文档用途：指导你把当前仓库中的已有成果，扩展成一套覆盖 Lite3 四足、Tron1 双轮足以及双平台真机部署的毕业论文主体工作流程。  
> 使用原则：先固化基线，再固化 Lite3，再补 Tron1，最后做真机部署与材料封装。  
> 本版重点：把 [nomad_mujoco_lite3_nav.py](../scripts/simulation/nomad_mujoco_lite3_nav.py) 作为现有主成果纳入流程，并新增 Tron1 MuJoCo 与 Lite3/Tron1 真机部署步骤。

## 6.1 第四步：完成数据集检查

### 操作目标

确认 GoStanford 数据可稳定支撑后续所有实验。

### 具体操作

```bash
python scripts/analysis/check_dataset.py
```

### 需要记录的内容

1. 总轨迹数。
2. 抽查轨迹是否正常。
3. 是否存在缺失图像或损坏的 `traj_data.pkl`。

### 当前已有结果与分析

结果文件：`results/day1/20260410_143018_dataset_check.txt`

当前抽查结果如下：

| 指标 | 结果 |
|---|---|
| 抽查轨迹数 | 5 |
| 异常轨迹数 | 0 |
| 总轨迹数 | 3696 |
| 抽查样本 | `no10vcF_10_0`、`no10vcF_11_0`、`no10vcF_11_1`、`no10vcF_12_0`、`no10vcF_16_0` |

这里每个值都应有明确含义：`抽查轨迹数` 表示人工实际复核了多少条轨迹；`异常轨迹数` 表示其中存在图像缺失、位姿不同步、`traj_data.pkl` 损坏等问题的轨迹数量；`总轨迹数` 表示当前数据集可供训练与评测使用的整体样本规模；`抽查样本` 则是被复核的具体轨迹 ID，便于后续追溯和复查。

1. 实验设计分析：这一步虽然不是性能对比实验，但它是所有后续实验的前置可靠性检查。设计这个抽查步骤的目的，不是为了证明模型性能，而是为了验证 `position`、`yaw`、图像帧三者是否一一对应，避免后续 DDIM、CFG 和视觉编码器实验把数据错误误判成算法退化。
2. 结果维度分析：当前抽查的 5 条轨迹全部为 `OK`，且 `n_pos = n_yaw = n_images`，说明最基本的数据同步关系成立；总轨迹数 3696 说明数据规模足以支撑基线、统计实验和后续 topomap 节点采样。如果这里出现 `traj_data.pkl` 缺失、位置和图像数不一致，那么后面出现的 loss 波动、轨迹异常、多样性异常都不能直接归因为算法。
3. 结论：当前数据集已经具备继续开展正式实验的条件。论文中可以把这一步写成“实验前数据一致性检查”，并用结果文件作为数据可用性的证据链起点。

## 6.2 第五步：重新跑离线基线推理

### 操作目标

把后面所有平台实验都建立在统一基线上。

### 具体操作

```bash
python scripts/analysis/offline_inference.py
```

### 需要记录的内容

1. 参数量。
2. 推理耗时。
3. 推理频率。
4. 导航模式和探索模式的轨迹结果。

### 注意事项

1. 基线结果必须保留时间戳目录。
2. 后续 Lite3 和 Tron1 的所有对比都要回到这里做参照。

### 当前已有结果与分析

结果文件：`results/day1/20260410_143032_offline_inference/summary.txt`

| 指标 | 结果 |
|---|---:|
| 模型参数量 | 19,049,675 |
| DDPM 推理时间 | 0.1250 s |
| 推理频率 | 8.0 Hz |
| 采样轨迹数 | 8 × 8 waypoints |
| 预测距离 | 11.6589 |

这些值在论文里也不能只报数字而不解释：`模型参数量` 表示模型需要存储和参与推理的参数总数，直接关系到显存、部署体积和推理成本；`DDPM 推理时间` 是一次完整扩散采样的平均耗时；`推理频率` 是其倒数，表示理论上每秒可完成多少次推理循环；`采样轨迹数 8 × 8 waypoints` 表示模型每次会采样 8 条候选轨迹，且每条轨迹预测 8 个未来 waypoint；`预测距离` 是距离头输出的平均距离估计量，用来观察条件编码和距离分支是否稳定。

1. 实验设计分析：基线离线推理的目的，是在不引入 DDIM、CFG、视觉编码器升级和 Lite3/Tron1 平台变量的前提下，先固定原始 NoMaD 的参考性能。这里之所以重点记录参数量、推理耗时和预测距离，是因为后续所有优化都必须同时回答两个问题：是否更快，是否没有明显破坏轨迹质量。
2. 结果维度分析：19.05M 参数说明当前 NoMaD 并不是一个轻量模型，因此 0.1250 s、8.0 Hz 的原始 DDPM 推理频率本身就构成了部署瓶颈，这也是后续必须做 DDIM 加速实验的直接动机。预测距离 11.6589 说明模型能够输出稳定的距离估计，后续如果某种优化导致该值剧烈漂移，同时轨迹质量恶化，就说明该优化不仅改变了采样速度，也改变了导航条件分布。
3. 结论：这组结果应作为全文统一基线。后面无论是 DDIM、CFG、视觉编码器升级，还是 Lite3/Tron1 仿真，都必须回到这一组基线量化指标进行比较，而不能只给出“看起来更快”或“似乎更稳”的主观判断。

这张表里的每一列都需要在正文中解释清楚：`样本数` 是参与统计的独立 case 数；`平均延迟(ms)` 是一次采样推理的平均耗时；`CI95(ms)` 是这个平均延迟的 95% 置信区间半宽，数值越小说明多次重复实验越稳定、均值越可信；`MSE vs DDPM-10` 是相对原始 `ddpm_10` 基线轨迹的均方误差，越小表示当前轨迹分布越接近基线；`Diversity` 衡量同一观测条件下多条采样轨迹的分散程度，过低可能表示模式坍缩，过高则可能表示轨迹发散；`Forward Progress` 表示轨迹沿主前进方向推进的平均距离，值越大通常说明朝目标推进能力越强；`加速比` 则是相对于 `ddpm_10` 的提速倍数。若正文进一步引用 `path_length_mean`，它表示整条预测轨迹的平均路径长度，用来判断提速后是否出现明显绕路或过度收缩。

1. 实验设计分析：DDIM 实验的核心变量是采样步数。设计这个参数变化的目的，是验证“减少扩散去噪步数”是否能在显著降低时延的同时，仍保持 waypoint 轨迹的可用性。因为 NoMaD 部署瓶颈首先来自扩散采样，若步数下降后质量损失很小，那么它就是最直接的实时化手段。
2. 结果维度分析：从 `ddpm_10` 到 `ddim_5/3/2`，延迟几乎单调下降，分别获得 2.08x、3.43x、4.84x 加速；这说明采样步数确实是主要时延来源。与此同时，`ddim_5`、`ddim_3`、`ddim_2` 的 `forward_progress_mean` 分别为 6.5257、6.6224、6.6471，并没有因为提速而明显恶化，反而略高于 `ddpm_10` 的 6.4998。真正的问题出现在 `ddim_1`：虽然延迟只有 4.5092 ms，但 `mse_vs_baseline_mean` 暴涨到 3.5168，`diversity` 也异常升到 4.7357，说明其采样轨迹已经明显偏离基线分布，不能再视为“同类轨迹的快速近似”。
3. 结论：就正式论文结论而言，`ddim_2` 是当前最优部署配置，因为它在 24 个 case 上实现了 4.84x 加速，同时仍维持与基线相近的路径长度和前进能力；`ddim_5` 可以作为更保守的稳健备选；`ddim_1` 不应作为最终推荐，只能写成极限加速参考点。

### TTS 推理时搜索优化 (NEW)

这里的 `TTS` 指的是 diffusion literature 中的 `test-time scaling / inference-time scaling`，不是语音任务中的 text-to-speech。  
它的核心思想是：在推理阶段投入更多候选轨迹预算，再用 verifier 对候选做评分选择，从而把一部分计算预算从“单条轨迹更长的去噪链”重新分配到“更多候选的搜索与筛选”上。

对于当前 NoMaD 链路，TTS 最合理的组件位置不是和 DDIM、CFG 完全并列，而是放在它们的外层：

1. `DDIM` 决定单条轨迹怎么采、采几步。
2. `CFG` 决定单条轨迹在采样时受目标引导多强。
3. `TTS` 决定已经采样出来的多条轨迹里，最终保留哪几条。

### TTS 代码入口

1. 快速验证：`scripts/experiments/tts_experiment.py`
2. 正式统计：`scripts/experiments/tts_stat_experiment.py`
3. 推理组件：`scripts/shared/nomad_inference.py`

### TTS 统计实验设计

这部分不建议只做 TTS 单因素，而应直接把 `DDIM / CFG / TTS` 作为推理层联合组件做统计矩阵。推荐矩阵如下：

1. 基线：`ddpm_10 + cfg=0.0 + tts=0`
2. DDIM 因素：`ddim_5`、`ddim_2`
3. CFG 因素：`w=0.0`、`0.5`、`1.0`
4. TTS 因素：`tts_budget=0`、`16`、`32`
5. 两两组合：`DDIM + CFG`、`DDIM + TTS`、`CFG + TTS`
6. 三者联合：`DDIM + CFG + TTS`

正式统计命令：

```bash
python scripts/experiments/tts_stat_experiment.py \
  --cases-per-suite 8 \
  --num-runs 8 \
  --ddim-steps-list 5,2 \
  --cfg-weights 0.0,0.5,1.0 \
  --tts-budgets 0,16,32 \
  --tts-topk 4 \
  --tts-verifier heuristic
```

### TTS 指标解释

1. `tts_budget`：推理时总共采样多少条候选轨迹，`0` 表示关闭 TTS。
2. `tts_topk`：verifier 打分后保留前几条候选轨迹。
3. `tts_verifier`：轨迹评分器类型，当前项目默认是导航任务启发式 verifier。
4. `verifier_score_mean`：最终保留轨迹的平均 verifier 分数。
5. `rank_score`：综合延迟、前向推进、横向偏移和平滑度得到的排序指标，用于筛选最终部署组合。

### 联合优化结果分析

1. 实验设计分析：联合实验的目的，不是重复前面的 DDIM 或 CFG 单因素结论，而是检验两者是否存在耦合效应。因为单独看 DDIM 可能得到“步数越少越快”，单独看 CFG 可能得到“`w=1.0` 更有引导性”，但真正部署时要同时满足实时性、前进能力、轨迹平滑性和横向稳定性，所以必须做联合网格搜索。
2. 结果维度分析：完整 20 组结果表明，所有 Top-5 配置都来自 DDIM 而不是 DDPM，说明部署端的最优区域已经明确转移到了 DDIM。`ddim2_w0.0` 之所以排第一，不是因为它在某一项上极端最优，而是因为它在延迟、前进距离、多样性和平滑度之间取得了最均衡的综合表现。虽然 `ddim2_w1.0` 和 `ddim2_w0.5` 在前进距离上略高，但它们的时延上升明显，综合评分反而低于无 CFG 版本，这说明 CFG 的收益是场景相关的，而不是全局普适的。
3. 结论：论文中的统一推荐配置应改为 `DDIM-2 + w=0.0`，这是真正由联合优化支持的全局最优解；`CFG w=1.0` 不能再写成默认最优，而应写成“在障碍更密集场景中的增强备选”，这个结论后面会由 Lite3 MuJoCo 的 medium 地图结果进一步支撑。

### Lite3 MuJoCo 结果分析

1. 实验设计分析：这一组实验的目的，是验证离线得到的最优配置 `DDIM-2 + w=0.0` 是否能迁移到闭环 MuJoCo 导航中，同时单独测试 `CFG w=1.0` 在更复杂障碍场景下是否带来额外收益。除此之外，还增加了探索模式、状态机导航和同地图多目标点导航，用于证明高层 NoMaD 不只是“单目标单脚本能跑”，而是可以迁移到分层系统结构与任务编排层。
2. 结果维度分析：首先，六组单目标导航全部 `Reached goal=True`，说明离线最优配置并没有在闭环里失效。其次，CFG 的收益明显具有场景相关性：在 easy 地图中，DDIM-2 + CFG 比 DDIM-2 少 3 步、少 0.351 m；在 hard 地图中，两者几乎一致；但在 medium 地图中，CFG 版本从 87 步下降到 61 步，路径从 7.360 m 缩短到 6.433 m，步数减少 26，路径缩短 0.927 m，说明适度引导主要在中等复杂障碍环境中体现价值。再次，状态机导航在 easy 地图上能稳定闭环；最后，导航主机在 easy 地图上完成了 `stand -> navigate(随机三目标点) -> explore -> estop` 的连续任务编排，其中三目标点导航以单地图随机选点、MuJoCo 内可视化 goal marker、在线生成 topomap 段的方式完成 48 步、5.280 m 到达，证明系统已经具备同地图多任务编排能力，而不是依赖手工拆分 topomap 目录。
3. 结论：Lite3 MuJoCo 结果支持两个层面的结论。算法层面，`DDIM-2 + w=0.0` 仍是默认部署配置，`CFG w=1.0` 更适合写成 medium 这类障碍场景的增强选项；系统层面，状态机版实现已经具备替代单脚本版写入论文系统章节的条件，而同地图多目标点导航与导航主机结果，则可以作为“导航模式支持多个目标顺序执行、并带有任务级编排”的直接证据。

### 多目标导航的正确实现方式

这一轮不再推荐“手工拆分多个 topomap 子目录”来做多目标 mission。
更合理、也更贴合 NoMaD 闭环机制的做法是：

1. 先固定一张 MuJoCo 地图。
2. 在同一张地图上随机采样若干个安全 `goal point`。
3. 在 MuJoCo 场景里把这些 `goal point` 可视化成 marker。
4. 在每个 `goal point` 位置采集对应的 `goal vision`。
5. 对每个目标点在线生成从当前位姿到该目标点的 topomap 段。
6. 状态机按顺序执行这些目标点，而不是人工维护多个分段目录。

这样做的好处是：

1. 目标图像、机器人当前观测、地图环境始终来自同一 MuJoCo 域。
2. 同一张地图内的多目标任务更自然，逻辑上是“地图上选点”，而不是“文件夹里切段”。
3. 生成的 `goal vision` 和在线 topomap 段可以直接复用到导航主机与共享 session。

### 结果分析

1. 实验设计分析：这一组实验的核心目标，不是比较谁的单步指标更好，而是验证视觉编码器替换能否真正迁移到 MuJoCo 多步闭环导航。这里固定了地图、底层控制、调度器和重复次数，只保留“编码器不同”这一主变量。
2. 结果维度分析：`EfficientNet-B0` 是当前这批结果里唯一稳定可靠的闭环方案，说明原始 NoMaD baseline 仍是当前最强部署基线。`ConvNeXt-Tiny` 在 easy 和 medium 上部分可用，但步数、路径距离和终点距离都明显偏大，说明虽然能到达，但路径效率较差。`DINOv2-Small` 0/9 的同时 `goal_dist` 仍低于 `ResNet-50`，表明它更像“能走但不收敛到目标”；`ResNet-50` 则表现为更严重的偏航和失稳。离线代理结果与闭环结果反转，也进一步说明单步代理指标不能直接替代闭环结论。
3. 结论：这组 MuJoCo 结果仍然有用，但它们目前更适合作为筛选阶段的闭环初筛结果和失败诊断证据，而不是最终公平排名。原因是这里的 `efficientnet_b0` 来自原始 NoMaD 训练链路，而其余编码器来自 backbone-suite 替换链路；只有在补入 `efficientnet_b0_suite` 并重跑后，才能得出框架内公平闭环结论。
4. **代码入口**：[mujoco_encoder_benchmark.py](../scripts/mujoco_encoder_benchmark.py)
5. **完整报告**：[benchmark_report.md](../results/benchmark/20260414_005304_encoder_benchmark/benchmark_report.md)

### 为什么 DINOv2 / ResNet-50 会出现 0% 成功率

这一点在论文里不能简单写成“这两个编码器差”，而要写成“在当前替换方法下闭环迁移失败”。更准确的解释如下：

1. 当前对比并不是完全 apples-to-apples。`efficientnet_b0` 使用的是原始 NoMaD baseline 训练链路，而 `dinov2_small`、`resnet50`、`convnext_tiny` 使用的是 backbone suite 替换链路；前者是原始架构，后者是“预训练 backbone + projection + NoMaD 头”的改造版，因此这里比较的不是单纯“编码器本体优劣”，还叠加了替换方法差异。
2. 当前升级编码器统一采用了 `freeze_backbone=True`、`lr=5e-5`、`epochs=100` 的保守配方。虽然训练轮数已经拉长，但 backbone 长期冻结仍意味着主要由投影层和高层头部去适配 NoMaD，视觉特征与距离头、扩散头之间依然可能没有真正对齐。
3. DINOv2 的失败模式更像“能走但不收敛到目标”。它的 `goal_dist` 约在 1.65 m 到 3.83 m，明显好于 ResNet-50 的 3.59 m 到 7.41 m，说明 DINOv2 不是完全不会前进，而是 topomap 匹配、局部子目标选择或多步误差累积出了问题。
4. ResNet-50 的失败模式更像“表征和导航头耦合不足导致明显偏航”。它在 easy 地图上都保持较大的终点误差，说明当前替换方式下它连最简单场景的闭环稳定性都没有建立起来。
5. 离线代理指标与闭环成功率发生反转，本身就提示我们：当前视觉编码器替换实验不能再只依赖 `encoder_comparison_experiment.py` 的单步统计，而必须把 MuJoCo 闭环 benchmark 作为主结论来源。
6. 本轮代码检查还发现，训练链路中距离预测头与视觉编码器是直接耦合的，而且此前训练/评测路径里存在输入形状不一致与学习率调度过快衰减的问题。这些问题已经修正，也说明 `dinov2_small` 和 `resnet50` 的 0% 成功率不能简单理解成“编码器本体更差”，而应理解成“替换方法仍在修正阶段”。

### 下一步做法

这一块建议不要写成“视觉编码器升级失败”，而要写成“视觉编码器升级方法已经建立，但当前替换配方尚未完成闭环收敛，下一步进入方法修正”。推荐按下面顺序推进：

1. **先做公平对照**：增加 `efficientnet_b0_suite`，不要再让 baseline 使用原始 NoMaD 训练入口、而升级编码器使用另一套训练入口。只有这样，才能判断到底是编码器本身更差，还是替换方法本身有偏差。
2. **做训练策略修正**：把 `dinov2_small` 和 `resnet50` 从“全程冻结 backbone”改成“两阶段微调”。建议先冻结 5~10 个 epoch 稳定头部，再解冻最后 1~2 个 stage 或最后几个 block，使用更小 backbone 学习率（如 `1e-5`）继续训练 40~80 epoch。
3. **统一 checkpoint 选择规则**：四个编码器都必须按同一规则选权重，例如统一使用 `ema_latest.pth` 或统一使用验证集最优 checkpoint，不能 baseline 用一个规则、backbone-suite 模型用另一个规则。
4. **把闭环验证前移**：后续不要只看离线 `forward_progress`、`lateral_abs`。建议每个编码器至少在 `easy/medium` 地图上做小规模闭环 sanity check，再决定是否继续长时间训练。
5. **增加诊断指标**：在 benchmark 中补充 topomap 节点选取日志、距离预测排序、waypoint 均值轨迹可视化。DINOv2 当前“接近目标但到不了”的现象很可能出在节点切换或距离头尺度，而不只是扩散采样本身。
6. **论文表述调整**：第四章不要再把“DINOv2 优于 EfficientNet”写成最终结论，而应写成“DINOv2 在离线代理指标上表现更优，但闭环部署失败，说明视觉编码器替换仍需完成策略头对齐与闭环验证”。这样既保留工作量，也避免结果自相矛盾。

## 7.8 第十四步补充：DDIM/CFG 跨编码器消融实验

### 实验目的

验证阶段一得到的 DDIM/CFG 最优配置是否对所有编码器通用，还是具有编码器依赖性。仅对闭环导航中有效的两个编码器（EfficientNet-B0、ConvNeXt-Tiny）做消融。

### 实验设计

2 个编码器 × 3 张地图 × 2 个调度器 (DDPM, DDIM-2) × 3 个 CFG 权重 (0.0, 0.5, 1.0) × 3 次重复 = 108 个实验。

```bash
cd ~/visualnav-transformer
MUJOCO_GL=egl QT_QPA_PLATFORM=offscreen python scripts/mujoco_encoder_benchmark.py \
  --encoders efficientnet_b0 convnext_tiny \
  --maps easy medium hard \
  --runs 3 --max-steps 300 \
  --schedulers ddpm ddim --ddim-steps 2 \
  --cfg-weights 0.0 0.5 1.0 \
  --cpu-cores 0-3 \
  --output-dir results/benchmark/ddim_cfg_encoder_ablation
```

### 实验结果

### 结果分析

1. **EfficientNet-B0 的最优配置是 DDIM-2 + CFG=0.5**。此配置在所有地图上步数最低（easy=45, medium=60.3, hard=73.7），路径距离最短，且保持 100% 成功率。相比 DDIM-2 + CFG=0.0，hard 地图步数从 121.3 降到 73.7（降幅 39%），终点距离从 2.63m 降到 0.42m。
2. **CFG=1.0 对 EfficientNet-B0 存在过引导风险**。DDIM-2 + CFG=1.0 在 easy 地图首次出现失败（2/3），说明过强引导导致行为不稳定。推荐 CFG=0.5 而非 1.0。
3. **阶段一的结论需要修正**。此前推荐的 DDIM-2 + w=0.0 并非闭环最优，DDIM-2 + w=0.5 在闭环导航中才是最优配置。
4. **ConvNeXt-Tiny 对 DDIM 高度依赖**。DDPM + CFG=0.0 完全失败（0/9），切换到 DDIM-2 后 easy 上恢复到 100%。DDIM-2 + CFG=0.5 是 ConvNeXt-Tiny 的最优配置。
5. **DDIM/CFG 优化效果具有编码器依赖性**。EfficientNet-B0 对调度器选择不敏感（DDPM 和 DDIM-2 差异不大），但 ConvNeXt-Tiny 对调度器极度敏感。这说明超参优化不能直接从一个编码器迁移到另一个。
6. **统一推荐配置**：对于所有编码器，DDIM-2 + CFG=0.5 是最稳健的通用配置。

## 7.9 第十四步补充：导航主机在线交互模式

### 新增功能

|---|---|
| `navigate [--max-steps N]` | 导航到目标 |

每条命令支持可选的调度器参数：`--scheduler`, `--ddim-steps`, `--cfg-weight`, `--goal-source`, `--num-goals`。

```bash
python scripts/deployment/nomad_navigation_host.py \
  --interactive --backend mujoco --map easy \
  --policy-config scripts/configs/vision_encoder/nomad_encoder_convnext_tiny.yaml \

```

### 已验证结果

1. 启动 → idle → `status`（显示位姿） → `quit`（退出）：✓
2. 启动 → `navigate --max-steps 50`（导航成功，到达 (4.933, 0.227)）→ `status` → `quit`：✓
3. 使用 DINOv2 编码器覆盖：✓ 可运行（但导航失败，与闭环基准实验结论一致）

### 设计要点

1. 在 idle 状态下，机器人保持站立并持续渲染相机画面，通过 `select.select` 非阻塞轮询 stdin。
2. 每次任务创建独立的 `Lite3System`，但共享 platform 和 session（平台不关闭不重建）。
3. 支持在运行中通过 `--policy-config` 和 `--policy-checkpoint` 指定不同编码器。

### 推荐的真机部署状态机

对于真机，不建议把 `navigate.py` 和 `explore.py` 仅仅理解成两个分散脚本。  
更适合论文表达、也更适合实际运行的方案，是把它们封装成同一套部署状态机：

1. `stand`：站立、稳定、等待进入具体任务。
2. `navigate`：执行 `mask = 0` 的目标导航。
3. `explore`：执行 `mask = 1` 的局部探索。
4. `recovery`：处理卡住、偏航、局部碰撞风险、观测异常。
5. `estop`：人工或安全逻辑触发的紧急停机。

当前仓库已经给出了 `navigate` 和 `explore` 两类入口，因此从工程实现角度看，这个状态机是完全可以搭出来的；论文里也建议直接把系统写成“可切换导航/探索模式的统一部署框架”。

### 导航主机设计思路

仅有状态机还不够，因为状态机解决的是“单次闭环执行”，而不是“整机任务编排”。更适合写进论文和落到工程里的方案，是在状态机之上再加一层导航主机：

1. 导航主机：负责选择后端、装载任务、切换模式、启动或停止状态机。
2. 状态机执行层：负责单次任务内的 NoMaD 推理、PD 桥接、底层控制和恢复逻辑。

这层主机已经在仓库中落成到 [nomad_navigation_host.py](../scripts/deployment/nomad_navigation_host.py)，其职责可以概括为：

| 主机职责 | 具体内容 |
|---|---|
| 后端接入 | 选择 `mujoco` 或 `real` 后端；MuJoCo 直接运行，真机通过 Python bridge 适配器接入 |
| 任务编排 | 读取单任务参数或任务计划文件，按顺序派发 `stand`、`navigate`、`explore`、`estop` |
| 状态机调度 | 为每个任务实例化状态机执行链，把任务配置传给 `Lite3System` |
| Capture 共享 | 维护共享 session，让 capture 队列在多个任务之间持续存在 |
| 结果管理 | 保存主机任务计划、执行摘要，并让状态机继续输出底层运行日志 |

这里要特别区分两个层次的“切换”：

1. 状态机内部切换：例如 `stand -> navigate -> recovery -> navigate`，这是执行期的闭环恢复。
2. 导航主机切换：例如 `stand task -> navigate task -> explore task -> estop task`，这是任务级调度。

从论文表述上说，导航主机不是替代状态机，而是位于状态机之上的“任务编排层”。这样写以后，你的系统结构就会更清晰：高层 NoMaD 与状态机负责自治执行，导航主机负责调度与平台接入。

### 导航主机与推理模块的协同关系

如果把整个系统按论文工程结构继续提炼，可以整理成下面两层：

1. 推理模块：
   由 [nomad_inference.py](../scripts/shared/nomad_inference.py) 实现，负责加载策略、处理图像、完成距离预测与扩散采样，并统一管理 `scheduler / ddim_steps / cfg_weight / tts_budget / tts_verifier / policy_config / policy_checkpoint`。
2. 部署模块：
   由 [nomad_mujoco_lite3_state_machine.py](../scripts/simulation/nomad_mujoco_lite3_state_machine.py)、[interfaces.py](../scripts/simulation/lite3_system/interfaces.py)、[system.py](../scripts/simulation/lite3_system/system.py)、[nomad_navigation_host.py](../scripts/deployment/nomad_navigation_host.py) 共同组成，负责状态机、任务计划、PD 桥接、平台执行和结果管理。

这样的分层有两个直接收益：

1. 更换视觉编码器训练得到的新策略时，不需要重写状态机和导航主机。
2. 调整部署推理配置时，不需要修改高层任务编排逻辑，只需改推理模块参数。

因此，论文里完全可以把这部分工作提炼成“推理模块设计与部署模块设计”两块，其中 DDIM、CFG、TTS、策略切换都属于前者；状态机、导航主机、PD 控制与真机/MuJoCo 接口都属于后者。

### 导航主机的 MuJoCo / 真机双后端设计

当前导航主机支持两种接入方式：

1. `mujoco` 后端：直接调用 Lite3 MuJoCo 状态机，适合仿真验证和任务计划联调。
2. `real` 后端：通过 `ExternalBridgePlatform` 适配 Python bridge，要求真机桥接模块提供相机、速度命令、位姿、速度、停车等接口。

这意味着导航主机本身不关心底层是 MuJoCo 还是 ROS/SDK 真机，只关心后端是否满足统一平台接口。也正因为如此，它可以把同一套 NoMaD + 状态机逻辑同时复用于仿真和真机。

### 导航主机设计结论

1. MuJoCo 仿真中的 Lite3 NoMaD 状态机部署已经存在，并且可以直接作为导航主机的执行后端。
2. 导航主机应被写成“状态机上层的统一任务编排器”，而不是另一个零散脚本。
3. 论文里可以把它作为仿真到真机迁移的关键工程层：同一套任务计划和状态机执行逻辑，通过不同后端适配器接入 MuJoCo 和真机。

### 导航模式建议设计成两层目标管理

如果你希望系统支持“多个目标”，建议在教程和论文中区分两层含义：

1. 局部层：一个 topomap 内部的多个节点。  
   这一层当前代码已经支持。系统会在局部窗口内根据距离预测选择当前子目标节点，再逐步推进到 `goal_node`。

2. 任务层：多个高层目标组成的 mission queue。  
   例如 `Goal A -> Goal B -> Goal C`。这一层现在不再建议手工拆分多个 topomap 目录，而是优先采用“同一张地图上采样多个目标点、为每个目标点生成 `goal vision` 和在线 topomap 段”的实现方式。

这里的表述要尽量准确：距离预测网络主要负责“当前激活候选集合内的局部子目标选择”，不要把它写成“直接完成全局多目标排序”。  
如果后面真的要做“最近目标优先”，最好明确说明这是你额外设计的调度策略，而不是原始 NoMaD 部署脚本自带的全局规划器。

### 注意事项

1. 先保留低速保守参数，不要一开始给高速度。
2. 先在遥操作与静态感知条件下确认相机图像正确，再进入 NoMaD 自主阶段。

## 10.2 第二十三步：梳理 Tron1 的平台专属桥接需求

### 必须明确的几个问题

## 10.3 第二十四步：按和 Lite3 相同的四层推进 Tron1 真机测试

## 13. 常见错误与规避方法

### 错误一：继续把 Lite3 写成“未来工作”

规避方法：

1. 直接以 [nomad_mujoco_lite3_nav.py](../scripts/simulation/nomad_mujoco_lite3_nav.py) 和 [nomad_mujoco_lite3_state_machine.py](../scripts/simulation/nomad_mujoco_lite3_state_machine.py) 为证据，把它们写进第五章主体。

### 错误二：Tron1 一上来就想全做完

规避方法：

1. 先跑 [nomad_mujoco_tron1_nav.py](../scripts/simulation/nomad_mujoco_tron1_nav.py) 固化资产与阶段计划。
2. 先做可运行版本，再补复杂场景。

### 错误三：真机部署前跳过静态感知检查

规避方法：

1. 先相机、再桥接、再低速、再导航。

### 错误四：把平台差异写得太虚

规避方法：

1. 明确写出 Lite3 和 Tron1 在桥接层、低层控制器和安全约束上的区别。

### 错误五：所有结果堆在一起没有证据链

规避方法：

1. 每个实验都保留结果目录。
2. 每个章节都建立脚本到图表的索引。

### 错误六：统计实验仍然只跑单次

规避方法：

1. DDIM 和 CFG 的正式结论统一使用统计版脚本。
2. 至少保留平均值、标准差和置信区间。

### 错误七：视觉编码器升级只比 DINOv2 和原始基线

规避方法：

1. 至少增加一种额外编码器作为补充对比。
2. 统一使用 [encoder_comparison_experiment.py](../scripts/experiments/encoder_comparison_experiment.py) 做评测。
