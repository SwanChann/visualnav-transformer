# 视觉编码器升级完整教程

## 1. 工作目标

这一部分工作的目标不是单纯“把 EfficientNet-B0 换掉”，而是同时完成两件事：

1. 建立统一的视觉编码器替换框架，能够在相同训练入口下比较不同编码器。
2. 在完成公平筛选后，选出适合继续做最终部署训练的候选编码器。

因此，这份教程只保留四类内容：

1. 要做什么。
2. 代码入口在哪里。
3. 当前结果说明了什么。
4. 下一步应该怎么推进。

---

## 2. 当前采用的统一框架

### 2.1 统一训练入口

1. 原始 baseline 配置：`scripts/configs/vision_encoder/nomad_encoder_efficientnet_b0.yaml`
2. backbone-suite 公平对照配置：`scripts/configs/vision_encoder/nomad_encoder_efficientnet_b0_suite.yaml`
3. DINOv2 配置：`scripts/configs/vision_encoder/nomad_encoder_dinov2_small.yaml`
4. ConvNeXt 配置：`scripts/configs/vision_encoder/nomad_encoder_convnext_tiny.yaml`
5. ResNet 配置：`scripts/configs/vision_encoder/nomad_encoder_resnet50.yaml`
6. 统一视觉编码器封装：`scripts/models/nomad_vint_backbone_suite.py`
7. 统一训练入口：`scripts/training/train_backbone_suite.py`
8. 权重准备脚本：`scripts/models/download_encoder_weights.py`
9. 多随机种子脚本：`scripts/training/run_encoder_seed_sweep.py`
10. 离线评测脚本：`scripts/experiments/encoder_comparison_experiment.py`
11. MuJoCo 闭环基准脚本：`scripts/mujoco_encoder_benchmark.py`

### 2.2 统一实验口径

当前四个编码器统一使用以下口径：

1. `batch_size = 32`
2. `eval_batch_size = 32`
3. `epochs = 100`
4. 默认开启 `wandb`

这保证了编码器对比至少在训练轮数和 batch 规模上保持一致，避免出现“某个编码器只是因为训练得更久、批量更大所以结果更好”的混淆。

## 3. 距离预测头与视觉编码器的关系

### 3.1 结论

距离预测头与视觉编码器是直接耦合的，不是彼此独立的模块。

### 3.2 代码层面的含义

在 NoMaD 中，视觉编码器先输出条件特征，然后：

1. 一路送给距离预测头。
2. 一路送给扩散策略头。

因此，只要视觉编码器发生变化，距离预测头输入的特征分布也会跟着变化，扩散头输入的特征分布也会同时变化。换句话说：

1. 距离预测器不能脱离视觉编码器单独理解。
2. 更换视觉编码器时，距离头必须一起重新训练。
3. 闭环导航失败时，问题可能来自编码器本身，也可能来自“编码器输出与距离头/扩散头没有重新对齐”。

### 3.3 本轮已经确认与修正的内容

当前训练链路已经做了两处必要修正：

1. 训练与评测阶段距离头输入形状已统一。
2. 学习率调度器按 epoch 正常推进，不再出现额外衰减。

因此，现在这套代码已经能够正常训练不同视觉编码器；当前结果中出现的差异，已经不再是“代码根本跑不通”的问题，而是方法效果和闭环对齐的问题。

## 4. 两阶段训练方案

## 4.1 第一阶段：统一框架筛选

### 目标

公平比较不同视觉编码器的潜力、稳定性和闭环可行性。

### 推荐对象

1. `efficientnet_b0_suite`
2. `dinov2_small`
3. `convnext_tiny`
4. `resnet50`

### 推荐命令

```bash
cd train
python ../scripts/training/train_backbone_suite.py --config ../scripts/configs/vision_encoder/nomad_encoder_efficientnet_b0_suite.yaml
python ../scripts/training/train_backbone_suite.py --config ../scripts/configs/vision_encoder/nomad_encoder_dinov2_small.yaml
python ../scripts/training/train_backbone_suite.py --config ../scripts/configs/vision_encoder/nomad_encoder_convnext_tiny.yaml
python ../scripts/training/train_backbone_suite.py --config ../scripts/configs/vision_encoder/nomad_encoder_resnet50.yaml
```

### 这一阶段的输出

1. 各编码器的训练日志与 checkpoint。
2. 离线代理评测结果。
3. MuJoCo 闭环基准结果。
4. 编码器失败模式分析。

这一步的目标是筛选候选方案，不是直接宣布“哪个编码器已经可以最终部署”。

## 4.2 第二阶段：最终部署训练

### 目标

把第一阶段筛选出的候选编码器，训练成真正可以进入 MuJoCo 和真机部署链路的最终策略。

### 建议做法

1. 只保留前 1 到 2 个候选编码器继续深入。
2. 统一 checkpoint 选择规则。
3. 把闭环 sanity check 前移，而不是只看离线表。
4. 对大 backbone 使用两阶段微调，而不是全程冻结。

### 推荐顺序

1. 先做 `efficientnet_b0_suite` 公平对照。
2. 再在 `dinov2_small`、`convnext_tiny`、`resnet50` 中保留闭环最有潜力的候选。
3. 对候选做部署导向训练。
4. 再进入 Lite3 MuJoCo 与真机链路。

## 5. 离线代理评测结果

结果目录：`results/day4/20260410_143729_encoder_comparison_experiment/`

### 5.1 当前已有正式结果

| 模型 | 样本数 | 平均延迟(ms) | Dist Pred Mean | Diversity | Forward Progress | Lateral Abs | Smoothness |
|---|---:|---:|---:|---:|---:|---:|---:|
| `efficientnet_b0` | 24 | 47.9319 | 12.9660 | 0.2609 | 7.3527 | 2.8197 | 0.1276 |
| `dinov2_small` | 24 | 42.9695 | 8.2408 | 0.5417 | 8.7765 | 1.8964 | 0.1215 |

### 5.2 指标含义

1. `平均延迟(ms)`：单次推理耗时。
2. `Dist Pred Mean`：距离头输出均值，用于观察距离分支尺度是否稳定。
3. `Diversity`：同一输入下多条候选轨迹的分散程度。
4. `Forward Progress`：轨迹沿主前进方向推进的平均距离。
5. `Lateral Abs`：轨迹横向偏移绝对值均值。
6. `Smoothness`：轨迹平滑度，越小通常越平顺。

### 5.3 结果分析

1. 实验设计分析：离线代理评测的目的是先比较单步条件编码质量和采样统计，不直接下闭环结论。
2. 结果维度分析：`dinov2_small` 在延迟、`Forward Progress` 和 `Lateral Abs` 上优于 `efficientnet_b0`，说明它在单步条件编码上确实有潜力。
3. 结论：离线代理结果只能说明 `dinov2_small` 值得继续研究，不能直接写成最终部署最优。

## 6. MuJoCo 闭环基准结果

结果目录：`results/benchmark/20260414_005304_encoder_benchmark/benchmark_report.md`

### 6.1 当前闭环结论

1. `efficientnet_b0` 是当前唯一稳定可靠的闭环部署编码器。
2. `convnext_tiny` 在 easy 和部分 medium 场景中可用，但整体稳定性不足。
3. `dinov2_small` 与 `resnet50` 在当前替换方法下闭环迁移失败。

### 6.2 为什么这些结果仍然有用

这批 MuJoCo 结果不能直接当“最终公平排名”，但仍然有两层价值：

1. 它们是筛选阶段的闭环初筛结果。
2. 它们是分析失败模式、指导下一步方法修正的直接证据。

### 6.3 为什么现在还不能下最终公平结论

原因不在于结果没价值，而在于当前对照关系还不完全公平：

1. `efficientnet_b0` 使用原始 NoMaD baseline 链路。
2. `dinov2_small`、`convnext_tiny`、`resnet50` 使用 backbone-suite 链路。
3. 这意味着当前比较里，既有编码器差异，也有替换框架差异。

因此，MuJoCo 闭环结果的正确写法应是：

1. baseline 仍然是当前最可靠部署方案。
2. 视觉编码器替换框架已经建立完成。
3. 升级编码器的闭环对齐问题已经被明确暴露出来。

---

## 7. 为什么 DINOv2 和 ResNet-50 会出现 0% 成功率

这一现象不能简单写成“这两个编码器更差”，更准确的表述是“在当前替换方法下闭环迁移失败”。

主要原因有四点：

1. 当前对比不是纯粹的编码器本体对比，还叠加了原始架构与统一替换架构的差异。
2. 当前训练配方较保守，长期冻结 backbone 会让投影层和高层头承受过多适配压力。
3. `dinov2_small` 更像“能走但不收敛到目标”，问题可能在 topomap 匹配、距离头尺度或多步误差累积。
4. `resnet50` 更像“表征与导航头耦合不足”，表现为明显偏航和闭环失稳。

---

## 8. 下一步做法

下一步不应写成“视觉编码器升级失败”，而应写成“视觉编码器升级方法已经建立，下一步进入公平对照与闭环修正阶段”。

建议按以下顺序推进：

1. 先补齐 `efficientnet_b0_suite` 的离线与 MuJoCo 闭环结果。
2. 统一四个编码器的 checkpoint 选择规则。
3. 对 `dinov2_small` 和 `resnet50` 做两阶段微调，而不是全程冻结。
4. 在训练中前移闭环 sanity check，不再只看离线表。
5. 在 benchmark 中增加 topomap 节点选择、距离排序和 waypoint 可视化日志。

---

## 9. 当前可写入论文的结论

这一部分现在最稳妥、也最有价值的结论有三条：

1. 已经建立了统一的视觉编码器替换框架，能够支持多编码器训练与对比。
2. 离线代理结果表明 `dinov2_small` 有潜力，但闭环 MuJoCo 结果表明当前最稳的部署编码器仍然是 `efficientnet_b0`。
3. 视觉编码器升级工作的价值，不应写成“已经找到最终更优编码器”，而应写成“已经建立替换方法，并通过闭环实验识别出策略头对齐和闭环收敛问题”。

如果后续 `efficientnet_b0_suite`、`dinov2_small` 或 `convnext_tiny` 能在统一框架下补齐闭环结果，再把其中表现最好的编码器写成正式升级方案。
