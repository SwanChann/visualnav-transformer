# 推理模块与闭环系统设计教程

## 1. 文档定位

这份文档只讲系统结构，不讲训练细节，也不展开 MuJoCo 结果表。目标是把“推理模块、状态机、导航主机、闭环系统”明确拆开，形成可以直接写进系统设计章节的文本。

---

## 2. 设计目标

这一部分设计要同时满足四个要求：

1. DDIM、CFG、checkpoint、视觉编码器切换必须集中控制。
2. 状态机不能依赖某一个固定策略权重。
3. 导航主机既能驱动 MuJoCo，也能驱动真机。
4. 更换由其他视觉编码器训练出来的 NoMaD 策略后，后续闭环代码仍能继续运行。

---

## 3. 推理模块的边界

### 3.1 代码入口

1. `scripts/shared/nomad_inference.py`
2. `scripts/simulation/lite3_system/interfaces.py`

### 3.2 推理模块只负责什么

推理模块负责的内容应固定为：

1. 加载 `policy_config`
2. 加载 `policy_checkpoint`
3. 图像预处理
4. 编码观测与目标图像
5. 距离预测
6. DDPM 或 DDIM 采样
7. CFG 引导
8. 输出 waypoint 队列

### 3.3 推理模块不负责什么

推理模块不负责：

1. 状态切换
2. PD 控制
3. 任务编排
4. MuJoCo 或真机接口管理

### 3.4 参数统一收口

当前推理侧关键参数已经集中在同一组件中：

1. `policy_config`
2. `policy_checkpoint`
3. `scheduler_kind`
4. `ddim_steps`
5. `cfg_weight`
6. `device`

这意味着 DDIM 步数、CFG 的 `w`、策略权重切换都不需要散落在多个脚本中修改。

## 4. 状态机设计

### 4.1 代码入口

1. `scripts/simulation/lite3_system/states.py`
2. `scripts/simulation/lite3_system/system.py`
3. `scripts/simulation/nomad_mujoco_lite3_state_machine.py`

### 4.2 当前核心状态

1. `idle`
2. `stand`
3. `navigate`
4. `explore`
5. `walk`
6. `recovery`
7. `estop`
8. `completed`
9. `failed`

### 4.3 状态机流转逻辑

典型导航流程为：

1. `idle -> stand`
2. `stand -> navigate`
3. `navigate -> recovery`，当出现卡滞
4. `navigate -> completed`，当到达目标
5. `navigate -> failed`，当跌倒、viewer 关闭或系统异常
6. 任意状态可转入 `estop`

### 4.4 状态机的职责

状态机负责把闭环执行过程组织成稳定、可恢复、可中断的过程，而不是只循环调用一次 `predict_action()`。

---

## 5. 导航主机设计

### 5.1 代码入口

1. `scripts/deployment/nomad_navigation_host.py`

### 5.2 导航主机的职责

导航主机位于状态机之上，负责：

1. 选择后端：`mujoco` 或 `real`
2. 装载任务计划
3. 启动 `stand`、`navigate`、`explore`、`estop`
4. 维护共享 session
5. 管理 capture 队列
6. 保存计划和运行摘要

### 5.3 在线交互模式

导航主机已经支持交互式命令：

1. `navigate`
2. `explore`
3. `stand`
4. `estop`
5. `capture`
6. `status`

这使系统不再局限于“提前写死一条命令”，而是能在运行过程中切换任务。

---

## 6. 闭环系统的数据流

完整闭环流程可以概括成八步：

1. 平台采集当前相机图像。
2. 上下文缓冲区维护最近若干帧观测。
3. 推理模块对观测和目标进行编码。
4. 距离头评估局部 topomap 节点或目标接近程度。
5. 扩散策略头采样候选轨迹。
6. 中层 PD 控制器将选中的 waypoint 转成速度命令。
7. 平台接口把控制命令下发到 MuJoCo 或真机。
8. 状态机根据执行结果决定继续导航、恢复、完成或失败。

---

## 7. 为什么这套设计支持不同视觉编码器

更换视觉编码器后，后续状态机和导航主机仍能工作，前提是新的策略仍满足 NoMaD 兼容接口。

原因是：

1. 状态机只消费“距离预测 + waypoint 结果”，不关心底层是 EfficientNet 还是 DINOv2。
2. 导航主机只调度任务和后端，不关心具体视觉编码器。
3. 编码器相关的差异被收口在推理模块的 `policy_config` 和 `policy_checkpoint` 中。

因此，系统结构上已经实现了“策略可替换、闭环代码不重写”的目标。

## 8. MuJoCo 与真机双后端设计

### 8.1 平台抽象

平台抽象统一由 `NavigationPlatformBase` 表达，并派生出两类实现：

1. MuJoCo 后端：`Lite3LowLevelPlatform`
2. 真机后端：`ExternalBridgePlatform`

### 8.2 双后端统一原则

1. 高层推理接口一致。
2. 中层 PD 控制接口一致。
3. 状态机流程一致。
4. 差异集中在底层平台桥接。

### 8.3 这一设计的意义

它保证了系统章节可以写成“同一高层架构，双后端复用”，而不是仿真和真机各写一套完全独立逻辑。

---

## 9. Capture 队列与目标管理

当前系统已支持共享 session 中的 capture 队列：

1. 可在运行时保存图像。
2. 可在 UI 中切换选中的 capture。
3. 可把选中的 capture 作为可视化目标参考。

对多目标导航而言，正确做法不是让 NoMaD 一次性输出全部目标的全局顺序，而是：

1. 导航主机管理任务队列。
2. 状态机逐目标执行。
3. 每次只把当前子目标交给 NoMaD。

这也是“多个目标顺序导航”的正确系统实现方式。

---

## 10. 可直接写入论文的结论

这一部分在论文中最适合写成两层设计：

1. 推理模块设计：
   统一管理策略权重、DDIM/CFG 参数和动作采样逻辑。
2. 部署模块设计：
   状态机、导航主机、中层 PD、平台接口共同组成闭环系统。

用一句话概括就是：

`DDIM / CFG / checkpoint / 视觉编码器切换属于推理模块；状态机、导航主机、PD 控制和 MuJoCo/真机接口属于部署模块。`
