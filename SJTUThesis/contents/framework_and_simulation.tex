\chapter{算法框架设计与仿真环境验证}

\section{本章研究目标与定位}

第三章主要回答的是“高层 NoMaD 策略如何设计、如何优化以及离线指标说明了什么”，但离线结果并不自动等价于系统结果。对于本文所面向的 Lite3 四足导航任务而言，真正需要继续回答的问题是：这些经过 DDIM、CFG 和视觉编码器筛选后的候选配置，能否接入统一推理模块、状态机、中层控制接口与平台后端，进一步形成一套能够连续运行的闭环系统。也就是说，从第三章进入第四章之后，研究对象已经从“单个模型”扩展为“模型与系统的组合体”。

因此，本章的定位是系统层和仿真层。系统层关注推理模块、状态机、导航主机和平台抽象接口如何组织；仿真层关注这些设计是否能够在 MuJoCo 环境中支撑 Lite3 完成单目标导航、探索模式和多目标任务。与第三章强调离线统计可比性不同，本章更强调模块边界清晰、接口一致、系统可恢复以及闭环行为可解释\cite{nomad2023}。只有当这些条件成立时，后续真机部署才具备现实基础。

从研究链条看，本章承担着承上启下的作用。一方面，它必须继承第三章给出的算法结论，例如 DDIM-2 更适合作为候选推理配置、CFG 应作为可调参数而不是固定默认项、视觉编码器切换需要与高层推理解耦；另一方面，它也必须为第五章提供足够稳定的系统底座，使同一套高层策略能够切换到真实平台后端继续工作。正因为如此，本章并不是“额外的工程实现附录”，而是本文验证 NoMaD 是否能够从算法结果走向足式闭环系统的关键章节。

\section{统一闭环系统的总体架构}

\subsection{总体分层思想}

结合项目中的现有实现，本文将 Lite3 仿真与真机的共用逻辑划分为四层：推理层、任务组织层、中层控制层和平台执行层。推理层负责根据当前视觉观测、目标图像和推理参数输出局部 waypoint 序列；任务组织层负责状态切换、任务队列、目标选择和异常恢复；中层控制层负责将高层 waypoint 转化为可执行的速度或姿态参考；平台执行层则负责把这些参考量下发到具体后端，包括 MuJoCo 仿真后端和真实机器人后端。

这种分层不是简单的代码分类，而是本文跨平台迁移能够成立的核心原因。如果高层直接输出强耦合于轮式平台的控制量，那么 NoMaD 很难迁移到 Lite3 四足系统\cite{nomad2023}；相反，当高层只输出局部轨迹，中层再吸收平台差异，系统就可以同时兼容 MuJoCo 与真机后端。这一点与 GNM、ViNT、NoMaD 等工作中强调的“高层输出更抽象的局部轨迹表示”是一致的\cite{gnm2022,vint2023,nomad2023}，也与 Diffusion Policy 所倡导的以动作序列作为策略输出的做法相呼应\cite{diffusionpolicy2023}。

在本文实现中，这一架构还服务于另一个更实际的目标，即让推理参数与系统逻辑分离。例如 DDIM 步数、CFG 权重、checkpoint 路径和视觉编码器类型，都应当在推理层统一控制，而不是分散到状态机、导航主机和 MuJoCo 脚本中。这样做既能减少实验中的隐藏变量，也能为真机部署保留统一接口。

\subsection{系统组成模块}

当前闭环系统主要由以下模块构成：

\begin{enumerate}
    \item 推理模块：负责加载 NoMaD 配置、模型权重、调度器和推理参数，并输出距离预测结果与 waypoint 队列；
    \item 状态机模块：负责组织 \texttt{idle}、\texttt{stand}、\texttt{navigate}、\texttt{explore}、\texttt{recovery}、\texttt{completed}、\texttt{failed} 等状态；
    \item 导航主机模块：负责统一管理后端选择、任务计划、多目标队列与交互命令；
    \item 平台接口模块：负责把高层输出映射为 MuJoCo 或真机可执行命令，并提供相机读取、位姿获取和安全停止等能力；
    \item 运行会话模块：负责统一管理 session、capture 队列、图像保存路径和运行摘要。
\end{enumerate}

对于系统设计而言，这些模块的价值不在于“模块越多越好”，而在于边界明确。推理模块不直接决定何时起立、何时恢复、何时终止；状态机不直接关心视觉编码器使用的是 EfficientNet 还是 DINOv2；导航主机不直接处理每一个 waypoint 的控制映射；平台接口也不需要理解 DDIM 和 CFG 的含义。正是这种边界清晰的模块化组织，使闭环实验具备了可复用性与可替换性。

\section{推理模块设计}

\subsection{推理模块的边界与职责}

本文中的推理模块并不负责整套系统的所有逻辑，而是专门承担“从图像条件到局部轨迹”的高层决策工作。更具体地说，它的输入包括历史观测图像、目标图像或候选节点图像、策略配置文件、模型 checkpoint、调度器类型以及 CFG 权重等参数；它的输出则包括候选目标距离预测结果和一段局部 waypoint 序列。换言之，推理模块的本质是一个统一的高层策略组件。

当前推理模块之所以要明确划定边界，是因为 NoMaD 本身已经足够复杂。它既包含视觉编码器、距离预测头，又包含扩散采样过程和可能的条件引导。如果再把状态切换、平台控制和任务编排也放进同一层，不仅代码会变得难以维护，实验结论也会失去可解释性。因此，本文将推理模块严格限制在“策略生成”范围内，把系统组织工作交给更外层模块处理。

\subsection{统一参数收口机制}

推理模块的一个关键设计是参数统一收口。当前系统中，核心推理参数集中在同一组件中管理，主要包括：

\begin{itemize}
    \item \texttt{policy\_config}；
    \item \texttt{policy\_checkpoint}；
    \item \texttt{scheduler\_kind}；
    \item \texttt{ddim\_steps}；
    \item \texttt{cfg\_weight}；
    \item \texttt{device}。
\end{itemize}

这样做有三点重要意义。

第一，它使 DDIM 和 CFG 等部署导向优化能够被视为推理参数，而不是“修改了系统结构”的额外分支。第二，它保证视觉编码器切换只需要更换配置与权重文件，而不会迫使状态机或导航主机重写逻辑。第三，它让仿真与真机可以复用同一高层推理入口，从而保证第四章和第五章之间的接口连续性。

从实验方法上看，这种统一参数设计同样重要。因为第三章已经表明，DDIM、CFG 和视觉编码器替换都会直接影响推理行为。如果这些参数散落在多个脚本中，后续仿真结果将难以解释；而当参数被统一收口后，系统层就能更清楚地回答“闭环变化究竟来自高层策略参数，还是来自后端和状态机逻辑”。

\subsection{为什么该设计支持多视觉编码器复用}

本文在第三章已经指出，视觉编码器与距离预测头、扩散策略头共享同一条件空间，因此更换视觉编码器会重构整条高层决策链路。但这种“强耦合”并不意味着系统层必须跟着重写。恰恰相反，只要新的策略仍然保持 NoMaD 兼容接口，状态机和导航主机就完全可以复用。

这是因为系统层只消费推理模块的输出结果，而不关心这些结果是由 EfficientNet、DINOv2、ConvNeXt 还是 ResNet 提供的。对于状态机而言，它关心的是“当前是否有轨迹输出”“是否达到目标”“是否需要恢复”；对于导航主机而言，它关心的是“当前任务是否完成”“下一个目标是谁”；而这些都建立在统一推理输出之上。因此，推理模块的边界划分不仅是工程选择，也直接服务于本文“先统一框架筛选编码器，再进入最终部署训练”的研究路线。

\section{状态机与导航主机设计}

\subsection{状态机设计目标}

在仿真和真机系统中，高层 NoMaD 推理并不是一次性调用的函数，而是要持续嵌入到闭环运行流程中。因此，系统必须回答一系列高于“生成轨迹”本身的问题，例如机器人何时起立、何时进入导航模式、何时进入探索模式、何时触发恢复、何时急停、何时判定任务完成。为了解决这些问题，本文引入了显式状态机设计。

状态机的目标并不是增加流程复杂度，而是为系统提供稳定、可恢复、可中断的运行秩序。对于 Lite3 这类足式平台而言，这一点尤为重要\cite{hwangbo2019anymal,lee2020learning}。因为一旦高层轨迹短暂异常、中层控制跟踪失败或平台姿态进入不安全状态，系统就不能继续“盲目前进”，而必须进入恢复逻辑或安全停止逻辑。也就是说，状态机是高层生成式策略进入足式闭环系统后的必要安全壳。

\subsection{状态定义与流转关系}

结合当前实现，系统核心状态可概括为：\texttt{idle}、\texttt{stand}、\texttt{navigate}、\texttt{explore}、\texttt{walk}、\texttt{recovery}、\texttt{estop}、\texttt{completed} 与 \texttt{failed}。其中，\texttt{idle} 表示尚未进入任务执行；\texttt{stand} 负责确保平台处于可控制姿态；\texttt{navigate} 和 \texttt{explore} 对应两种主要高层推理模式；\texttt{recovery} 负责处理卡滞、偏离或局部异常；\texttt{estop} 则提供最高优先级的安全停止；\texttt{completed} 与 \texttt{failed} 分别表示任务完成和任务终止。

典型流程可以概括为：
\[
\texttt{idle} \rightarrow \texttt{stand} \rightarrow \texttt{navigate/explore} \rightarrow \texttt{completed/failed}
\]
在导航或探索过程中，如果系统检测到目标可达性下降、位置卡滞、步数超限或控制异常，则可切换到 \texttt{recovery}；若恢复无效或接收到强制停止命令，则切换到 \texttt{estop} 或 \texttt{failed}。这种设计保证闭环运行不再只是“循环调一次 NoMaD”，而是具备了任务级行为组织能力。

\subsection{导航主机的角色}

如果说状态机解决的是“每一个任务内部如何运行”，那么导航主机解决的则是“系统整体该跑什么任务”。在本文设计中，导航主机位于状态机之上，负责选择后端类型、装载任务计划、管理单目标或多目标队列、组织探索模式、接收交互式命令以及维护运行会话。

这种层级划分非常重要。因为多目标导航本质上不是让 NoMaD 一次性对多个目标做联合规划，而是由导航主机把长程任务拆成一系列当前子任务，再交给状态机和 NoMaD 逐一执行。换言之，多目标导航的“顺序组织”属于导航主机职责，而单个子目标下“下一小段路怎么走”才属于 NoMaD 职责。这也解释了为什么本文能够在同一系统下同时支持单目标导航、探索模式和多目标任务，而无需切换完全不同的高层算法。

\section{MuJoCo 仿真平台设计}

\subsection{为什么选择 MuJoCo 作为闭环验证环境}

本文在系统层验证中选用 MuJoCo 作为主要仿真平台。原因在于，MuJoCo 在接触动力学、控制频率和可调仿真接口方面具有较好的研究适用性\cite{mujoco2012}，能够较稳定地承载足式机器人这类需要持续闭环控制的系统，并被广泛用于足式运动学习与控制策略验证\cite{hwangbo2019anymal,rl_locomotion_rudin2022}。更重要的是，它允许本文在较低风险条件下把 NoMaD 推理模块、状态机、中层控制映射和平台接口整合起来，观察高层策略进入闭环后的真实表现。

从研究方法上看，MuJoCo 在本文中并不是“能看见机器人动起来”的演示环境，而是系统证据的产生环境。第三章给出的离线结果只能说明候选配置在轨迹统计层面有潜力，而 MuJoCo 则进一步回答这些候选配置能否在任务执行、状态切换和控制接口约束下保持成立。正因如此，MuJoCo 是第三章与第五章之间不可缺少的桥梁。

\subsection{仿真系统的五层组成}

当前 Lite3 MuJoCo 仿真可以被划分为五层。第一层是场景与 topomap 层，负责提供视觉节点、地图和任务环境；第二层是高层 NoMaD 推理层，负责根据视觉条件生成轨迹；第三层是中层 waypoint 到控制量映射层，负责把局部轨迹变为速度参考；第四层是底层平台接口层，负责与 MuJoCo 机器人模型交互；第五层是状态机与系统循环层，负责组织整体运行逻辑。

这五层结构与前文提出的系统分层高度一致，但 MuJoCo 仿真让它们第一次在统一闭环中联合运行。也就是说，仿真层不是额外增加的一套逻辑，而是系统架构的第一个完整后端。后续真机部署能够复用第四章的设计，正是因为这套架构已经在仿真中完成了先行验证。

\subsection{仿真任务类型}

根据当前项目结果与实验脚本，MuJoCo 仿真已覆盖四类任务：单目标导航、探索模式、状态机导航以及同地图多目标导航。单目标导航用于验证给定 topomap 与推理配置时，机器人能否从当前位置闭环接近目标；探索模式用于验证 goal mask 对应的“无明确目标条件”是否仍能支撑连续探索；状态机导航用于验证高层 NoMaD 能否嵌入完整状态流；同地图多目标导航则用于验证导航主机是否能够连续执行多个子任务而无需人工重启。

这些任务并不是彼此独立的零散 demo，而是构成了从“基本闭环可行”到“任务级系统可行”的逐步验证链条。单目标导航回答系统最基本的问题；探索模式回答 goal mask 在部署侧是否真的有意义；状态机导航回答高层策略能否被安全组织；多目标导航进一步回答系统是否具备较高层次的任务编排能力。

\section{MuJoCo 闭环实验与结果分析}

\subsection{实验设计}

本章仿真实验主要围绕三个层面展开。第一，验证经过第三章筛选的推理配置能否迁移到 MuJoCo 闭环；第二，验证状态机与导航主机是否能在任务级别稳定组织流程；第三，验证单目标导航、探索模式和多目标任务是否均可通过同一高层 NoMaD 逻辑驱动。基于当前结果目录，本文采用 easy、medium、hard 等地图场景，比较 DDIM-2 与 DDIM-2 + CFG 的闭环表现，并额外考察状态机导航和多目标导航任务。

在这一实验设计中，核心指标包括步数、总路径长度以及是否到达目标。步数反映闭环任务完成所需的控制周期；总路径长度反映机器人累计实际行程，而非简单的起终点直线距离；是否到达则反映任务级别结果。与第三章的离线代理指标相比，这些指标更贴近系统层验证逻辑，因为它们已经把推理、控制映射和平台执行共同纳入考察范围。

\subsection{已有仿真结果}

根据当前项目中已经形成的 MuJoCo 结果，DDIM-2 配置下 Lite3 已能够在 easy、medium、hard 三类地图上完成单目标导航；在加入 CFG $w=1.0$ 后，medium 场景的闭环步数进一步下降，说明适度条件引导在中等复杂度场景中仍然具有一定收益。探索模式实验表明，在 goal mask 对应的无明确目标条件下，系统仍能连续产生可执行轨迹；状态机导航实验与三目标点任务实验则表明，系统已经具备从单次局部导航扩展到任务级闭环组织的能力。

这些结果非常重要，因为它们意味着第三章中的算法优化并没有在系统层全部失效。尤其是 DDIM-2 的成功闭环说明，扩散策略在经过采样加速后，已经足以进入 Lite3 仿真的实时区间；多目标导航成功则进一步说明导航主机的任务拆分思想是成立的，即 NoMaD 不需要直接优化整个全局任务序列，也能通过“当前子目标 + 当前局部轨迹”的方式逐步完成任务。

\subsection{结果分析与系统层结论}

从系统层结论看，当前 MuJoCo 结果首先证明了 NoMaD 并非只能作为离线模型存在，而是能够在闭环控制中持续输出具有任务意义的高层轨迹。其次，它证明状态机和导航主机并非“为了工程完整性而强行添加”的模块，而是能够实际改变系统能力边界的必要组件。没有状态机，就难以组织 stand、recovery 与 estop；没有导航主机，就难以把多目标任务与探索模式纳入统一流程。

进一步地，MuJoCo 结果也揭示了系统结论的边界。当前闭环成功并不意味着所有配置都同样适合真机部署，也不意味着视觉编码器第一阶段实验已经给出最终答案。仿真层所能证明的是：高层 NoMaD、统一推理模块、状态机和导航主机的组合在 Lite3 后端上已经具备系统可行性；而关于真实感知噪声、网络通讯时延和平台硬件稳定性，则仍需第五章继续验证。

\section{本章小结}

本章从系统层与仿真层对本文研究进行了进一步推进。首先，围绕统一推理模块、状态机、导航主机与平台接口，构建了一个可兼容 MuJoCo 与真机后端的分层闭环架构，并明确了各模块的职责边界。其次，说明了为何推理参数需要统一收口、为何状态机与导航主机是足式系统中的必要组成部分，以及为何多目标任务应由任务调度层组织而不是由 NoMaD 直接端到端完成。再次，结合 MuJoCo 平台介绍了闭环仿真的验证目标、系统组成与任务类型，并对已有 Lite3 仿真结果进行了系统层分析。
