# 论文全文语言表达问题检查报告

检查对象：`论文/main.tex` 及 `论文/contents` 下各章正文。  
检查重点：将偏“项目说明、代码报告、调试记录”的表达，调整为更符合毕业论文的学术表述；同时检查口语化、绝对化、英文术语未中文化、大小写不统一等问题。

## 一、总体判断

全文整体已经具备论文结构，但部分章节仍保留了工程调试记录和代码说明的语言痕迹。尤其在第二、三、四章中，存在“脚本”“目录”“当前系统”“结果通过”“case”“Checklist”“跑”等偏实现过程或实验记录的词语。这类表达本身不一定错误，但如果直接出现在论文正文中，会削弱论文的学术性，使读者感觉作者在描述一个项目代码仓库，而不是在论证一项研究工作。

本次未在当前正文中发现“本项目代码中设置”这一完全相同的原句，但发现了多处同类型表达。建议全文统一采用“本文”“本研究”“本文构建的系统”“实验流程”“实验记录”“部署流程”“推理模块”“控制链路”等论文表述，避免直接以代码、脚本、目录为叙述主体。

## 三、建议全文统一替换的表达习惯

以下不是简单的机械替换，而是建议在相应语境中统一论文口吻：

| 原表达习惯 | 建议表达 |
|---|---|
| 本项目、当前项目、项目代码 | 本文、本研究、本文系统、本文构建的系统 |
| 代码中、脚本中、程序里 | 在本文方法中、在实验流程中、在推理流程中 |
| 部署脚本、采集脚本、统计脚本 | 部署流程、采集程序、统计流程、评价流程 |
| 文件、目录 | 实验资产、数据路径、配置文件、图像节点文件 |
| 当前系统、当前实现 | 本文系统、本文采用的实现方案、本文构建的实验平台 |
| 跑、跑通、结果通过 | 执行、完成验证、结果表明、验证了 |
| case | 实验样例、测试样例、实验组 |
| Checklist | 完整性检查、部署检查、实验前置检查 |
| 好处、坏处 | 优势、限制、代价、影响 |
| 证明了 | 表明、说明、初步验证、结果支持 |
| 只能、完全、一定 | 倾向于、基本、在本文实验条件下、在一定程度上 |

## 四、优先修改顺序

1. 优先修改第四章真机实验部分，因为该章“脚本、目录、Checklist、结果通过、当前系统”等工程化表达最多，最容易被认为是项目报告。
2. 其次修改第三章仿真与系统框架部分，重点处理“当前实现”“零散脚本”“部署脚本”“好处/坏处”等表达。
3. 再修改第二章算法实验部分，重点统一英文指标和工程术语，如 `case`、`top-k`、`batch size`、`backbone`、`跑` 等。
4. 最后修改摘要和结论，避免代码状态名、绝对化结论和过长贡献段落影响论文整体观感。

## 五、建议的统一写作口径

后续修改正文时，可以采用以下统一口径：

“本文面向四足机器人视觉目标导航任务，构建了由视觉推理、状态机调度、底层速度控制和真机通信组成的闭环系统。对于工程实现细节，正文只保留与方法结构、实验流程和结果分析直接相关的部分；对于代码文件、脚本、目录和调试检查等内容，则转化为实验流程、数据组织和系统模块的论文表述。”

这一口径可以帮助全文从“项目实现说明”转为“研究方法与实验验证说明”。
