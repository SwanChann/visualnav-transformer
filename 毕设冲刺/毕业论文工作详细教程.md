# 基于 NoMaD 的毕业论文工作详细教程

> 文档用途：指导你把当前仓库中的已有成果，扩展成一套覆盖 Lite3 四足、Tron1 双轮足以及双平台真机部署的毕业论文主体工作流程。  
> 使用原则：先固化基线，再固化 Lite3，再补 Tron1，最后做真机部署与材料封装。  
> 本版重点：把 [nomad_mujoco_lite3_nav.py](../scripts/simulation/nomad_mujoco_lite3_nav.py) 作为现有主成果纳入流程，并新增 Tron1 MuJoCo 与 Lite3/Tron1 真机部署步骤。
> 当前执行约束：本机为 Ubuntu 20.04 部署环境，系统 Python 命令为 `python3`，且当前系统 Python 缺少 `torch`，因此训练任务不能作为本机验收项；训练相关内容在本机只做代码、路径、结果证据审计。

## 1. 教程目标

按照本教程执行后，你最终应得到五类成果：

1. 可复现的 NoMaD 基线与优化结果。

3. 可直接用于论文第五章的 Lite3 MuJoCo 联合导航证据链。
4. 可执行的 Tron1 MuJoCo 实施路线与实验入口。
5. Lite3 与 Tron1 真机部署的分平台流程、检查项和测试记录。

## 3. 本教程的配套脚本

### 3.1 原有辅助脚本

2. [path_audit.py](../scripts/tooling/path_audit.py)

### 3.2 本轮新增脚本

1. [nomad_mujoco_tron1_nav.py](../scripts/simulation/nomad_mujoco_tron1_nav.py)  
   用途：检查 Tron1 MuJoCo 资产、导出实施清单、固定目录结构。

2. [nomad_real_deployment_checklist.py](../scripts/deployment/nomad_real_deployment_checklist.py)  
   用途：为 Lite3 和 Tron1 生成真机部署检查清单。

3. [ddim_stat_experiment.py](../scripts/experiments/ddim_stat_experiment.py)  
   用途：为 DDIM 加速实验提供多次重复、跨测试套件统计分析、均值和置信区间结果。

4. [cfg_stat_experiment.py](../scripts/experiments/cfg_stat_experiment.py)  
   用途：为 CFG 引导实验提供多次重复、跨测试套件统计分析和趋势图。

5. [nomad_vint_backbone_suite.py](../scripts/models/nomad_vint_backbone_suite.py)  
   用途：统一封装 DINOv2、ConvNeXt、ResNet 等视觉编码器，保持 NoMaD 接口一致。

6. [train_backbone_suite.py](../scripts/training/train_backbone_suite.py)  
   用途：训练不同视觉编码器版本的 NoMaD。

7. [encoder_comparison_experiment.py](../scripts/experiments/encoder_comparison_experiment.py)  
   用途：对多种视觉编码器 checkpoint 做统一导航评测。

8. [nomad_mujoco_lite3_state_machine.py](../scripts/simulation/nomad_mujoco_lite3_state_machine.py)  
   用途：将 Lite3 MuJoCo 导航拆分成高层 NoMaD、中层 PD、底层 locomotion + MuJoCo 的三层接口，并显式实现状态机。

9. [interfaces.py](../scripts/simulation/lite3_system/interfaces.py)  
   用途：集中定义高层接口、中层 PD 接口和低层平台接口。

10. [states.py](../scripts/simulation/lite3_system/states.py)  
   用途：分别实现 `idle`、`standup`、`navigate`、`explore`、`recovery_back`、`recovery_turn`、`completed`、`failed` 状态。

11. [system.py](../scripts/simulation/lite3_system/system.py)  
   用途：整合三层接口、mission queue、topomap 管理和状态机主循环。

### 3.3 分类路径约定

从这版开始，`scripts/` 下优先使用分类后的 canonical path：

3. `scripts/models/`：视觉编码器与模型封装。

8. `scripts/shared/`：多脚本复用的公共模块。

根目录旧脚本仍然保留，主要用于兼容旧命令；教程里后续统一使用分类路径。

### 3.4 这些新增脚本为什么必要

因为本轮教程中新增了两类以前仓库里没有固定入口的工作：

## 5. 阶段一：环境和路径固化

这一阶段不只是准备环境，而是给后面的 Lite3、Tron1 和真机部署建立统一底座。

## 5.1 第一步：建立训练环境与部署环境边界

### 操作目标

明确 Ubuntu 22.04 负责训练与离线实验，Ubuntu 20.04 负责部署与机器人接口。

### 具体操作

训练环境：

```bash
conda create -n nomad-thesis python=3.8 -y
conda activate nomad-thesis
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

部署环境：

```bash
conda create -n nomad-deploy python=3.8 -y
conda activate nomad-deploy
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

### 注意事项

1. Ubuntu 20.04 侧优先承担 ROS、MuJoCo、真机接口与低速部署测试。
2. Ubuntu 22.04 侧优先承担训练、离线实验、结果整理。
3. 不要混用日志输出目录。
4. 如果 MuJoCo 和机器人 SDK 依赖版本不同，分别在两侧固定版本，不要强行合并环境。

## 5.2 第二步：运行环境检查脚本

4. 权重文件是否存在。

### 注意事项

2. 这一步的报告后面可以作为论文中的实验环境准备证据。

## 5.3 第三步：运行路径审计脚本

### DDIM × CFG 联合优化实验 (NEW — 正式论文结果)

单独调 DDIM 步数和 CFG 强度无法找到全局最优。联合网格搜索 20 种组合：

```bash
python scripts/joint_ddim_cfg_experiment.py --cases-per-suite 8 --num-runs 8
```

**实验设计**:
- 搜索空间: DDIM steps {10(DDPM), 10, 5, 3, 2} × CFG w {0.0, 0.5, 1.0, 2.0} = **20 种组合**
- 每种配置: 24 cases × 8 runs × 8 samples
- 综合评分: 延迟 30% + 前进距离 30% + 平滑度 15% + 横向偏移 15% + 多样性 10%

**联合优化结果 Top-5**:

| 排名 | 配置 | 综合评分 | 延迟(ms) | 加速比 | 前进距离 |
|---:|---|---:|---:|---:|---:|
| 1 | **DDIM-2 w=0.0** | **5.6477** | **6.18** | **4.84×** | 8.089 |
| 2 | DDIM-3 w=0.0 | 5.3648 | 9.12 | 3.28× | 8.076 |
| 3 | DDIM-2 w=0.5 | 4.9877 | 11.39 | 2.63× | 8.106 |
| 4 | DDIM-2 w=1.0 | 4.9853 | 11.44 | 2.62× | 8.122 |
| 5 | DDIM-5 w=0.0 | 4.9851 | 14.94 | 2.00× | 8.032 |

**最优配置**: `--scheduler ddim --ddim-steps 2` (6.18ms, 4.84× 加速)
**避障增强**: `--scheduler ddim --ddim-steps 2 --cfg-weight 1.0` (仿真中减少绕行步数)

**论文中引用的代码入口**:
[joint_ddim_cfg_experiment.py](../scripts/joint_ddim_cfg_experiment.py)

## 6.4 第七步：决定 DINOv2 在论文中的地位

这一阶段也不建议只做 “baseline vs DINOv2” 的单一升级。  
更合理的做法是把视觉编码器升级扩展成一组对比实验。

### DINOv2 单独训练入口

```bash
cd train
python ../scripts/training/train_dinov2.py -c config/nomad_dinov2.yaml
cd ..
```

### 多视觉编码器统一训练入口

```bash
cd train
python ../scripts/training/train_backbone_suite.py --config config/nomad_dinov2.yaml --backbone dinov2_small --freeze-backbone --pretrained-backbone
python ../scripts/training/train_backbone_suite.py --config config/nomad_dinov2.yaml --backbone convnext_tiny --freeze-backbone --pretrained-backbone
python ../scripts/training/train_backbone_suite.py --config config/nomad_dinov2.yaml --backbone resnet50 --freeze-backbone --pretrained-backbone
cd ..
```

### 建议纳入对比的视觉编码器

1. `efficientnet_b0`
   原始 NoMaD 基线。

2. `dinov2_small`
   当前已经实现的升级方向，重点验证自监督 ViT 表征。

3. `convnext_tiny`
   代表现代 CNN / ConvNet 路线。

4. `resnet50`
   代表经典残差网络路线，可作为较强 CNN 基线。

### 多视觉编码器统一评测入口

```bash
python scripts/experiments/encoder_comparison_experiment.py \
  --model-spec efficientnet_b0=deployment/model_weights/nomad/nomad.pth \
  --model-spec dinov2_small=train/logs/nomad-backbone-suite/<dinov2_run>/ema_19.pth \
  --model-spec convnext_tiny=train/logs/nomad-backbone-suite/<convnext_run>/ema_19.pth \
  --model-spec resnet50=train/logs/nomad-backbone-suite/<resnet_run>/ema_19.pth
```

### 视觉编码器对比实验设计要求

1. 不能只比单次推理时间。
2. 至少比较：
   `latency_ms`、`dist_pred_mean`、`diversity`、`forward_progress_mean`、`smoothness_mean`
3. 至少在多个测试套件上比较结果，而不是单条轨迹。
4. 训练时要固定高层 NoMaD 结构，只改变视觉编码器，避免变量过多。

## 7.5 第十三步：补探索模式与纯运动模式

### 探索模式

```bash

```

### 纯运动测试

```bash
python scripts/simulation/nomad_mujoco_lite3_nav.py --mode walk-test
python scripts/simulation/nomad_mujoco_lite3_state_machine.py --mode walk-test
```

探索模式这一节建议在教程里直接写明原理，而不要只写成“没有目标也能跑”。  
训练阶段 `goal_mask_prob = 0.5` 的作用，本质上是让模型同时学习两类分布：有目标时的 `p(a | o, g)`，以及遮蔽目标时的 `p(a | o)`。  
因此，部署时把 `mask` 设为 `1`，并不是让模型“瞎走”，而是调用它在训练中学到的局部可通行先验，让它根据当前图像和历史上下文生成一组合理的短时 waypoint 轨迹。

这里还要避免另一个常见误解：探索模式不是对视野中的所有空位做几何枚举，也不是显式 frontier search。  
更准确地说，它是从当前观测条件下采样若干条可能轨迹；如果前方只有一条明显通路，轨迹会更集中，如果前方有多个可行方向，采样结果才可能体现出一定多样性。

### 这两步的作用

1. 探索模式用于说明 NoMaD 不只支持目标导航，还支持无目标探索。
2. 纯运动测试用于证明低层 locomotion policy 本身可运行。

### 注意事项

1. 评估探索模式时，不要只截图最终执行的单个 waypoint，最好同时保存多条采样轨迹，这样更容易说明模型学到的是“局部探索分布”而不是单一路径。
2. 如果探索结果总是过于保守或总朝单一方向前进，优先检查训练数据分布和采样数量，而不是直接下结论说 `goal mask` 失效。

### 推荐的真机部署状态机

对于真机，不建议把 `navigate.py` 和 `explore.py` 仅仅理解成两个分散脚本。  
更适合论文表达、也更适合实际运行的方案，是把它们封装成同一套部署状态机：

3. `explore`：执行 `mask = 1` 的局部探索。
4. `recovery`：处理卡住、偏航、局部碰撞风险、观测异常。
5. `estop`：人工或安全逻辑触发的紧急停机。

当前仓库已经给出了 `navigate` 和 `explore` 两类入口，因此从工程实现角度看，这个状态机是完全可以搭出来的；论文里也建议直接把系统写成“可切换导航/探索模式的统一部署框架”。

### 导航模式建议设计成两层目标管理

如果你希望系统支持“多个目标”，建议在教程和论文中区分两层含义：

1. 局部层：一个 topomap 内部的多个节点。  
   这一层当前代码已经支持。系统会在局部窗口内根据距离预测选择当前子目标节点，再逐步推进到 `goal_node`。

2. 任务层：多个高层目标组成的 mission queue。  
   例如 `Goal A -> Goal B -> Goal C`。这一层建议单独做一个任务管理器：当前 topomap 或目标节点完成后，再切换到下一项任务。

这里的表述要尽量准确：距离预测网络主要负责“当前激活候选集合内的局部子目标选择”，不要把它写成“直接完成全局多目标排序”。  
如果后面真的要做“最近目标优先”，最好明确说明这是你额外设计的调度策略，而不是原始 NoMaD 部署脚本自带的全局规划器。

## 13. 常见错误与规避方法

### 错误一：继续把 Lite3 写成“未来工作”

规避方法：

1. 直接以 [nomad_mujoco_lite3_nav.py](../scripts/simulation/nomad_mujoco_lite3_nav.py) 和 [nomad_mujoco_lite3_state_machine.py](../scripts/simulation/nomad_mujoco_lite3_state_machine.py) 为证据，把它们写进第五章主体。

### 错误二：Tron1 一上来就想全做完

规避方法：

1. 先跑 [nomad_mujoco_tron1_nav.py](../scripts/simulation/nomad_mujoco_tron1_nav.py) 固化资产与阶段计划。
2. 先做可运行版本，再补复杂场景。

### 错误三：真机部署前跳过静态感知检查

规避方法：

1. 先相机、再桥接、再低速、再导航。

### 错误四：把平台差异写得太虚

规避方法：

1. 明确写出 Lite3 和 Tron1 在桥接层、低层控制器和安全约束上的区别。

### 错误五：所有结果堆在一起没有证据链

规避方法：

1. 每个实验都保留结果目录。
2. 每个章节都建立脚本到图表的索引。

### 错误六：统计实验仍然只跑单次

规避方法：

1. DDIM 和 CFG 的正式结论统一使用统计版脚本。
2. 至少保留平均值、标准差和置信区间。

### 错误七：视觉编码器升级只比 DINOv2 和原始基线

规避方法：

1. 至少增加一种额外编码器作为补充对比。
2. 统一使用 [encoder_comparison_experiment.py](../scripts/experiments/encoder_comparison_experiment.py) 做评测。
