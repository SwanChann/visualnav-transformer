# 基于 NoMaD 的毕业论文工作详细教程

> 文档用途：指导你把当前仓库中的已有成果，扩展成一套覆盖 Lite3 四足、Tron1 双轮足以及双平台真机部署的毕业论文主体工作流程。  
> 使用原则：先固化基线，再固化 Lite3，再补 Tron1，最后做真机部署与材料封装。  
> 本版重点：把 [nomad_mujoco_lite3_nav.py](../scripts/nomad_mujoco_lite3_nav.py) 作为现有主成果纳入流程，并新增 Tron1 MuJoCo 与 Lite3/Tron1 真机部署步骤。

---

## 1. 教程目标

按照本教程执行后，你最终应得到五类成果：

1. 可复现的 NoMaD 基线与优化结果。
2. 可直接用于论文第四章的 DDIM、CFG、DINOv2 结果整理。
3. 可直接用于论文第五章的 Lite3 MuJoCo 联合导航证据链。
4. 可执行的 Tron1 MuJoCo 实施路线与实验入口。
5. Lite3 与 Tron1 真机部署的分平台流程、检查项和测试记录。

## 3. 本教程的配套脚本

### 3.1 原有辅助脚本

1. [env_check.py](../scripts/env_check.py)
2. [path_audit.py](../scripts/path_audit.py)
3. [thesis_result_summary.py](../scripts/thesis_result_summary.py)

### 3.2 本轮新增脚本

1. [nomad_mujoco_tron1_nav.py](../scripts/nomad_mujoco_tron1_nav.py)  
   用途：检查 Tron1 MuJoCo 资产、导出实施清单、固定目录结构。

2. [nomad_real_deployment_checklist.py](../scripts/nomad_real_deployment_checklist.py)  
   用途：为 Lite3 和 Tron1 生成真机部署检查清单。

3. [ddim_stat_experiment.py](../scripts/ddim_stat_experiment.py)  
   用途：为 DDIM 加速实验提供多次重复、跨测试套件统计分析、均值和置信区间结果。

4. [cfg_stat_experiment.py](../scripts/cfg_stat_experiment.py)  
   用途：为 CFG 引导实验提供多次重复、跨测试套件统计分析和趋势图。

5. [nomad_vint_backbone_suite.py](../scripts/nomad_vint_backbone_suite.py)  
   用途：统一封装 DINOv2、ConvNeXt、ResNet 等视觉编码器，保持 NoMaD 接口一致。

6. [train_backbone_suite.py](../scripts/train_backbone_suite.py)  
   用途：训练不同视觉编码器版本的 NoMaD。

7. [encoder_comparison_experiment.py](../scripts/encoder_comparison_experiment.py)  
   用途：对多种视觉编码器 checkpoint 做统一导航评测。

### 3.3 这两个新增脚本为什么必要

因为本轮教程中新增了两类以前仓库里没有固定入口的工作：

1. Tron1 MuJoCo 导航。
2. Lite3/Tron1 真机部署。

教程里的步骤不能只写“去实现”，必须在仓库里给出明确入口。

## 5. 阶段一：环境和路径固化

这一阶段不只是准备环境，而是给后面的 Lite3、Tron1 和真机部署建立统一底座。

## 5.1 第一步：建立训练环境与部署环境边界

### 操作目标

明确 Ubuntu 22.04 负责训练与离线实验，Ubuntu 20.04 负责部署与机器人接口。

### 具体操作

训练环境：

```bash
conda create -n nomad-thesis python=3.8 -y
conda activate nomad-thesis
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

部署环境：

```bash
conda create -n nomad-deploy python=3.8 -y
conda activate nomad-deploy
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

### 注意事项

1. Ubuntu 20.04 侧优先承担 ROS、MuJoCo、真机接口与低速部署测试。
2. Ubuntu 22.04 侧优先承担训练、离线实验、结果整理。
3. 不要混用日志输出目录。
4. 如果 MuJoCo 和机器人 SDK 依赖版本不同，分别在两侧固定版本，不要强行合并环境。

## 5.2 第二步：运行环境检查脚本

### 操作目标

检查数据集、模型权重、部署目录、结果目录是否齐全。

### 具体操作

```bash
python scripts/env_check.py --save
```

### 需要重点确认

1. `dataset_root` 是否存在。
2. `trajectory_count` 是否正常。
3. `deployment/config/models.yaml` 是否存在。
4. 权重文件是否存在。

### 注意事项

1. 如果权重路径在不同脚本中不一致，先记录下来，不要跳过。
2. 这一步的报告后面可以作为论文中的实验环境准备证据。

## 5.3 第三步：运行路径审计脚本

### 操作目标

找出所有可能影响多平台迁移和真机部署的路径耦合。

### 具体操作

```bash
python scripts/path_audit.py --save
```

### 优先处理范围

1. `scripts/` 目录下的实验脚本。
2. `train/config/` 中的训练配置。
3. `deployment/` 中的权重路径和配置路径。

### 注意事项

1. 你后面会在 Lite3、Tron1 和真机之间反复切换，路径统一非常关键。
2. 这一步是论文第三章的一部分，不是杂活。

### 具体操作

```bash
python scripts/check_dataset.py
```

### 需要记录的内容

1. 总轨迹数。
2. 抽查轨迹是否正常。
3. 是否存在缺失图像或损坏的 `traj_data.pkl`。

## 6.2 第五步：重新跑离线基线推理

### 操作目标

把后面所有平台实验都建立在统一基线上。

### 具体操作

```bash
python scripts/offline_inference.py
```

### 需要记录的内容

1. 参数量。
2. 推理耗时。
3. 推理频率。
4. 导航模式和探索模式的轨迹结果。

### 注意事项

1. 基线结果必须保留时间戳目录。
2. 后续 Lite3 和 Tron1 的所有对比都要回到这里做参照。

## 6.3 第六步：收口 DDIM 与 CFG 结果

这一阶段不建议再只保留“单轨迹、单次运行”的结果。  
为了让第四章更有统计可靠性，建议把原有脚本保留为快速验证入口，把新增统计脚本作为正式论文结果入口。

### DDIM 快速实验

```bash
python scripts/ddim_experiment.py
```

### DDIM 统计实验

```bash
python scripts/ddim_stat_experiment.py --cases-per-suite 8 --num-runs 8
```

### DDIM 统计实验设计要求

1. 至少对 `short`、`medium`、`long` 三个测试套件分别评估。
2. 每个配置至少重复 8 次，记录平均值、标准差和 95% 置信区间。
3. 至少比较 `ddpm_10`、`ddim_10`、`ddim_5`、`ddim_3`、`ddim_2`、`ddim_1`。
4. 主要指标至少包含：
   `latency_ms`、`mse_vs_baseline`、`diversity`、`path_length_mean`、`forward_progress_mean`

### 论文中引用的代码入口

[ddim_stat_experiment.py](../scripts/ddim_stat_experiment.py)

### CFG 快速实验

```bash
python scripts/cfg_experiment.py
```

### CFG 统计实验

```bash
python scripts/cfg_stat_experiment.py --cases-per-suite 8 --num-runs 8 --num-steps 10
```

### CFG 统计实验设计要求

1. 至少比较 `w=-1.0`、`0.0`、`0.5`、`1.0`、`2.0`、`4.0`。
2. 每个引导强度至少重复 8 次，不能只看单次采样结果。
3. 至少在多个测试套件上统计：
   `short`、`medium`、`long`
4. 主要指标至少包含：
   `latency_ms`、`shift_vs_w0`、`diversity`、`forward_progress_mean`、`lateral_abs_mean`

### 论文中引用的代码入口

[cfg_stat_experiment.py](../scripts/cfg_stat_experiment.py)

### 需要形成的统一结论

1. 哪个 DDIM 步数最适合作为部署版本。
2. 哪个 CFG 引导强度最适合目标导航。
3. 哪些配置可以直接迁移到 Lite3/Tron1 的 MuJoCo 和真机工作中。
4. 哪些结论在多个测试套件和多次重复运行后依然稳定成立。

## 6.4 第七步：决定 DINOv2 在论文中的地位

这一阶段也不建议只做 “baseline vs DINOv2” 的单一升级。  
更合理的做法是把视觉编码器升级扩展成一组对比实验。

### DINOv2 单独训练入口

```bash
cd train
python ../scripts/train_dinov2.py -c config/nomad_dinov2.yaml
cd ..
```

### 多视觉编码器统一训练入口

```bash
cd train
python ../scripts/train_backbone_suite.py --config config/nomad_dinov2.yaml --backbone dinov2_small --freeze-backbone --pretrained-backbone
python ../scripts/train_backbone_suite.py --config config/nomad_dinov2.yaml --backbone convnext_tiny --freeze-backbone --pretrained-backbone
python ../scripts/train_backbone_suite.py --config config/nomad_dinov2.yaml --backbone resnet50 --freeze-backbone --pretrained-backbone
cd ..
```

### 建议纳入对比的视觉编码器

1. `efficientnet_b0`
   原始 NoMaD 基线。

2. `dinov2_small`
   当前已经实现的升级方向，重点验证自监督 ViT 表征。

3. `convnext_tiny`
   代表现代 CNN / ConvNet 路线。

4. `resnet50`
   代表经典残差网络路线，可作为较强 CNN 基线。

### 多视觉编码器统一评测入口

```bash
python scripts/encoder_comparison_experiment.py \
  --model-spec efficientnet_b0=deployment/model_weights/nomad/nomad.pth \
  --model-spec dinov2_small=train/logs/nomad-backbone-suite/<dinov2_run>/ema_19.pth \
  --model-spec convnext_tiny=train/logs/nomad-backbone-suite/<convnext_run>/ema_19.pth \
  --model-spec resnet50=train/logs/nomad-backbone-suite/<resnet_run>/ema_19.pth
```

### 视觉编码器对比实验设计要求

1. 不能只比单次推理时间。
2. 至少比较：
   `latency_ms`、`dist_pred_mean`、`diversity`、`forward_progress_mean`、`smoothness_mean`
3. 至少在多个测试套件上比较结果，而不是单条轨迹。
4. 训练时要固定高层 NoMaD 结构，只改变视觉编码器，避免变量过多。

### 论文中引用的代码入口

1. [nomad_vint_backbone_suite.py](../scripts/nomad_vint_backbone_suite.py)
2. [train_backbone_suite.py](../scripts/train_backbone_suite.py)
3. [encoder_comparison_experiment.py](../scripts/encoder_comparison_experiment.py)

### 决策规则

1. 如果 `dinov2_small` 在统计结果上稳定优于 `efficientnet_b0`，就把它写成第四章正式子模块。
2. 如果 `convnext_tiny` 或 `resnet50` 也表现良好，就把第四章写成“视觉编码器对比与升级研究”，而不是只写 DINOv2。
3. 如果多个编码器差异不显著，就如实写成“对比实验表明编码器升级带来的提升有限”。

### 注意事项

1. 不要让 DINOv2 拖垮主线节奏。
2. 视觉编码器对比必须建立在统一评测脚本之上，不能不同模型用不同评测流程。
3. 当前最重要的是先把 Lite3 和 Tron1 主线补齐。

## 6.5 第八步：统一汇总现有结果

```bash
python scripts/thesis_result_summary.py --save
```

### 目的

1. 统一整理基线、DDIM、CFG 结果。
2. 将统计版 DDIM / CFG 结果与快速验证结果区分开。
3. 将视觉编码器对比结果纳入同一张实验索引表。
4. 为后续 Lite3 与 Tron1 章节准备表格草稿。

## 7. 阶段三：Lite3 MuJoCo 联合导航固化

这一阶段是本教程和旧教程最大的区别。  
之前 Lite3 只是“一个仿真方向”；现在 [nomad_mujoco_lite3_nav.py](../scripts/nomad_mujoco_lite3_nav.py) 已经是核心代码成果。

## 7.1 第九步：先做代码级链路梳理

### 操作目标

把 Lite3 MuJoCo 联合导航拆解成论文可写的五层结构。

### 需要重点阅读的代码位置

1. [nomad_mujoco_lite3_nav.py](../scripts/nomad_mujoco_lite3_nav.py)
2. [deployment/src/navigate.py](../deployment/src/navigate.py)
3. [deployment/src/pd_controller.py](../deployment/src/pd_controller.py)

### 你要整理出的链路

1. MuJoCo 相机渲染。
2. NoMaD topomap 定位。
3. 扩散采样输出轨迹。
4. `waypoint -> velocity`。
5. Lite3 低层 RL locomotion。
6. 关节级仿真执行与恢复状态机。

### 注意事项

1. 这一步不要急着跑实验，先把代码对应关系搞清楚。
2. 你后面写论文第五章时，核心图就是从这里提炼出来的。

## 7.2 第十步：检查 Lite3 MuJoCo 依赖资产

### 需要确认的文件

1. `sdk_deploy/src/Lite3_sdk_deploy/Lite3_description/lite3_mjcf/mjcf/Lite3.xml`
2. `sdk_deploy/src/Lite3_sdk_deploy/policy/policy.onnx`
3. NoMaD 权重文件

### 建议操作

先人工确认资产，再进入运行阶段。

### 注意事项

1. 如果 ONNX locomotion policy 缺失，不要直接跑 `navigate` 模式。
2. Lite3 MuJoCo 这部分要保持“仿真资产、NoMaD 权重、结果目录”三者分开管理。

## 7.3 第十一步：先跑 topomap 生成

### 操作目标

为 `navigate` 模式准备固定地图导航节点。

### 具体操作

```bash
python scripts/nomad_mujoco_lite3_nav.py --mode generate-topomap --map easy
python scripts/nomad_mujoco_lite3_nav.py --mode generate-topomap --map medium
python scripts/nomad_mujoco_lite3_nav.py --mode generate-topomap --map hard
```

### 注意事项

1. 每个地图都要保留单独的 topomap 目录。
2. 如果后续要写论文图示，优先保留 easy 和 hard 两个难度。

## 7.4 第十二步：跑 Lite3 MuJoCo 导航主实验

### 推荐起步顺序

先从可视化版本开始：

```bash
python scripts/nomad_mujoco_lite3_nav.py --mode navigate --map easy
```

再跑无头模式与更复杂地图：

```bash
python scripts/nomad_mujoco_lite3_nav.py --mode navigate --map medium --no-gui
python scripts/nomad_mujoco_lite3_nav.py --mode navigate --map hard --scheduler ddim --ddim-steps 5
```

### 需要记录的内容

1. 导航是否到达目标。
2. 总步数与总轨迹长度。
3. 卡住恢复事件次数。
4. 推理模式是 DDPM 还是 DDIM。
5. easy、medium、hard 三个地图下的差异。

### 注意事项

1. 优先记录 `summary.txt`、`trajectory.txt`、`velocities.txt`。
2. 如果 hard 地图不稳定，不要第一时间改算法，先分析恢复逻辑和子目标推进逻辑。

## 7.5 第十三步：补探索模式与纯运动模式

### 探索模式

```bash
python scripts/nomad_mujoco_lite3_nav.py --mode explore --map medium
```

### 纯运动测试

```bash
python scripts/nomad_mujoco_lite3_nav.py --mode walk-test
```

### 这两步的作用

1. 探索模式用于说明 NoMaD 不只支持目标导航，还支持无目标探索。
2. 纯运动测试用于证明低层 locomotion policy 本身可运行。

## 7.6 第十四步：整理 Lite3 小节的论文证据链

### 你至少要保留

1. 一张系统结构图。
2. 一张 Lite3 导航流程图。
3. 一张 easy/medium/hard 结果对比表。
4. 一张恢复次数或失败类型统计表。
5. 结果目录路径索引。

### 注意事项

1. 第五章的 Lite3 小节一定要从“已实现的代码链”出发写。
2. 不要把 Lite3 写成“未来准备做”，这已经不符合仓库事实。

## 8. 阶段四：Tron1 MuJoCo 导航实现

这一阶段是本轮新增的主体工作。  
目标不是直接一口气做出完整 Tron1 产品，而是把它变成一个有目录、有脚本入口、有实现步骤、有验证结果的正式工作包。

## 8.1 第十五步：先生成 Tron1 实施清单

### 操作目标

先确认 Tron1 资产是否齐全，再决定怎么实现。

### 具体操作

```bash
python scripts/nomad_mujoco_tron1_nav.py --mode validate-assets
python scripts/nomad_mujoco_tron1_nav.py --mode export-manifest --save
```

### 这一步会帮你确认什么

1. NoMaD 权重位置。
2. Tron1 MuJoCo 模型应放在哪。
3. Tron1 低层控制器或 ONNX 策略应放在哪。
4. 相机配置与说明文件应放在哪。

### 注意事项

1. 如果脚本提示必需资产缺失，就先补目录结构，不要直接写仿真主逻辑。
2. Tron1 的第一步不是写代码，而是固定资产规范。

## 8.2 第十六步：参照 Lite3 拆分 Tron1 的五层结构

### 参照文件

1. [nomad_mujoco_lite3_nav.py](../scripts/nomad_mujoco_lite3_nav.py)
2. [nomad_mujoco_tron1_nav.py](../scripts/nomad_mujoco_tron1_nav.py)

### 你需要明确的 Tron1 组件

1. MuJoCo 机器人模型入口。
2. Tron1 相机视角和图像预处理。
3. NoMaD 高层推理接口。
4. `waypoint -> wheel-legged command` 桥接。
5. Tron1 低层控制器接口。

### 注意事项

1. 这一层一定要单独写笔记，因为论文里 Lite3 和 Tron1 的关键差别就在这里。
2. 不要直接把 Lite3 的 `velocity -> locomotion policy` 生搬到 Tron1。

## 8.3 第十七步：完成 Tron1 MuJoCo 代码实施

### 建议顺序

1. 先完成机器人模型加载。
2. 再完成相机渲染。
3. 再完成高层 NoMaD 调用。
4. 最后接中间桥接层和低层控制器。

### 推荐实现思路

1. 复用 Lite3 中的 NoMaD 推理部分。
2. 保留 DDPM/DDIM 调度选择接口。
3. 把平台差异集中到桥接层。
4. 在 Tron1 中额外加入速度和姿态安全约束。

### 注意事项

1. Tron1 的首个版本优先完成“能跑起来并生成日志”，不要一开始追求复杂场景。
2. 如果 Tron1 低层控制器暂时不能闭环，可以先做开环桥接验证，但必须如实记录。

## 8.4 第十八步：做 Lite3 vs Tron1 对比

### 你需要至少做的对比项

1. 同类 topomap 任务下的导航成功情况。
2. 同类地图下的恢复次数。
3. 高层推理延迟是否一致。
4. 中间桥接层复杂度差异。

### 注意事项

1. 这一部分是第五章最能体现“多形态研究”的内容。
2. 你不需要追求指标绝对碾压，而是要把平台差异讲清楚。

## 13. 常见错误与规避方法

### 错误一：继续把 Lite3 写成“未来工作”

规避方法：

1. 直接以 [nomad_mujoco_lite3_nav.py](../scripts/nomad_mujoco_lite3_nav.py) 为证据，把它写进第五章主体。

### 错误二：Tron1 一上来就想全做完

规避方法：

1. 先跑 [nomad_mujoco_tron1_nav.py](../scripts/nomad_mujoco_tron1_nav.py) 固化资产与阶段计划。
2. 先做可运行版本，再补复杂场景。

### 错误三：真机部署前跳过静态感知检查

规避方法：

1. 先相机、再桥接、再低速、再导航。

### 错误四：把平台差异写得太虚

规避方法：

1. 明确写出 Lite3 和 Tron1 在桥接层、低层控制器和安全约束上的区别。

### 错误五：所有结果堆在一起没有证据链

规避方法：

1. 每个实验都保留结果目录。
2. 每个章节都建立脚本到图表的索引。

### 错误六：统计实验仍然只跑单次

规避方法：

1. DDIM 和 CFG 的正式结论统一使用统计版脚本。
2. 至少保留平均值、标准差和置信区间。

### 错误七：视觉编码器升级只比 DINOv2 和原始基线

规避方法：

1. 至少增加一种额外编码器作为补充对比。
2. 统一使用 [encoder_comparison_experiment.py](../scripts/encoder_comparison_experiment.py) 做评测。
