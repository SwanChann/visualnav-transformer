# 基于 NoMaD 的毕业论文工作详细教程

> 文档用途：指导你把当前仓库中的已有成果，扩展成一套覆盖 Lite3 四足、Tron1 双轮足以及双平台真机部署的毕业论文主体工作流程。  
> 使用原则：先固化基线，再固化 Lite3，再补 Tron1，最后做真机部署与材料封装。  
> 本版重点：把 [nomad_mujoco_lite3_nav.py](../scripts/simulation/nomad_mujoco_lite3_nav.py) 作为现有主成果纳入流程，并新增 Tron1 MuJoCo 与 Lite3/Tron1 真机部署步骤。
> 当前执行约束：本机为 Ubuntu 20.04 部署环境，系统 Python 命令为 `python3`，且当前系统 Python 缺少 `torch`，因此训练任务不能作为本机验收项；训练相关内容在本机只做代码、路径、结果证据审计。

## 5. 阶段一：环境和路径固化

这一阶段不只是准备环境，而是给后面的 Lite3、Tron1 和真机部署建立统一底座。

## 5.1 第一步：建立训练环境与部署环境边界

### 操作目标

明确 Ubuntu 22.04 负责训练与离线实验，Ubuntu 20.04 负责部署与机器人接口。

### 具体操作

训练环境：

```bash
conda create -n nomad-thesis python=3.8 -y
conda activate nomad-thesis
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

部署环境：

```bash
conda create -n nomad-deploy python=3.8 -y
conda activate nomad-deploy
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

### 注意事项

1. Ubuntu 20.04 侧优先承担 ROS、MuJoCo、真机接口与低速部署测试。
2. Ubuntu 22.04 侧优先承担训练、离线实验、结果整理。
3. 不要混用日志输出目录。
4. 如果 MuJoCo 和机器人 SDK 依赖版本不同，分别在两侧固定版本，不要强行合并环境。

## 6. 阶段二：NoMaD 基线与优化结果收口

这部分对应论文第三章和第四章的前半部分。

## 6.1 第四步：完成数据集检查

### 操作目标

确认 GoStanford 数据可稳定支撑后续所有实验。

### 具体操作

```bash
python scripts/analysis/check_dataset.py
```

### 需要记录的内容

1. 总轨迹数。
2. 抽查轨迹是否正常。
3. 是否存在缺失图像或损坏的 `traj_data.pkl`。

### 当前已有结果与分析

结果文件：`results/day1/20260410_143018_dataset_check.txt`

当前抽查结果如下：

| 指标 | 结果 |
|---|---|
| 抽查轨迹数 | 5 |
| 异常轨迹数 | 0 |
| 总轨迹数 | 3696 |
| 抽查样本 | `no10vcF_10_0`、`no10vcF_11_0`、`no10vcF_11_1`、`no10vcF_12_0`、`no10vcF_16_0` |

1. 实验设计分析：这一步虽然不是性能对比实验，但它是所有后续实验的前置可靠性检查。设计这个抽查步骤的目的，不是为了证明模型性能，而是为了验证 `position`、`yaw`、图像帧三者是否一一对应，避免后续 DDIM、CFG 和视觉编码器实验把数据错误误判成算法退化。
2. 结果维度分析：当前抽查的 5 条轨迹全部为 `OK`，且 `n_pos = n_yaw = n_images`，说明最基本的数据同步关系成立；总轨迹数 3696 说明数据规模足以支撑基线、统计实验和后续 topomap 节点采样。如果这里出现 `traj_data.pkl` 缺失、位置和图像数不一致，那么后面出现的 loss 波动、轨迹异常、多样性异常都不能直接归因为算法。
3. 结论：当前数据集已经具备继续开展正式实验的条件。论文中可以把这一步写成“实验前数据一致性检查”，并用结果文件作为数据可用性的证据链起点。

## 6.2 第五步：重新跑离线基线推理

### 操作目标

把后面所有平台实验都建立在统一基线上。

### 具体操作

```bash
python scripts/analysis/offline_inference.py
```

### 需要记录的内容

1. 参数量。
2. 推理耗时。
3. 推理频率。
4. 导航模式和探索模式的轨迹结果。

### 注意事项

1. 基线结果必须保留时间戳目录。
2. 后续 Lite3 和 Tron1 的所有对比都要回到这里做参照。

### 当前已有结果与分析

结果文件：`results/day1/20260410_143032_offline_inference/summary.txt`

| 指标 | 结果 |
|---|---:|
| 模型参数量 | 19,049,675 |
| DDPM 推理时间 | 0.1250 s |
| 推理频率 | 8.0 Hz |
| 采样轨迹数 | 8 × 8 waypoints |
| 预测距离 | 11.6589 |

1. 实验设计分析：基线离线推理的目的，是在不引入 DDIM、CFG、视觉编码器升级和 Lite3/Tron1 平台变量的前提下，先固定原始 NoMaD 的参考性能。这里之所以重点记录参数量、推理耗时和预测距离，是因为后续所有优化都必须同时回答两个问题：是否更快，是否没有明显破坏轨迹质量。
2. 结果维度分析：19.05M 参数说明当前 NoMaD 并不是一个轻量模型，因此 0.1250 s、8.0 Hz 的原始 DDPM 推理频率本身就构成了部署瓶颈，这也是后续必须做 DDIM 加速实验的直接动机。预测距离 11.6589 说明模型能够输出稳定的距离估计，后续如果某种优化导致该值剧烈漂移，同时轨迹质量恶化，就说明该优化不仅改变了采样速度，也改变了导航条件分布。
3. 结论：这组结果应作为全文统一基线。后面无论是 DDIM、CFG、视觉编码器升级，还是 Lite3/Tron1 仿真，都必须回到这一组基线量化指标进行比较，而不能只给出“看起来更快”或“似乎更稳”的主观判断。

### DDIM 当前已有结果与分析

快速验证结果文件：`results/day2/20260410_143043_ddim_results.txt`  
正式统计结果文件：`results/day2/20260410_143136_ddim_stat_experiment/ddim_overall_summary.csv`

| 配置 | 样本数 | 平均延迟(ms) | CI95(ms) | MSE vs DDPM-10 | Diversity | Forward Progress | 加速比 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `ddpm_10` | 24 | 39.9790 | 1.3748 | 0.0000 | 0.2512 | 6.4998 | 1.00x |
| `ddim_10` | 24 | 38.0260 | 0.6034 | 0.0062 | 0.3175 | 6.4686 | 1.05x |
| `ddim_5` | 24 | 19.2581 | 0.4319 | 0.0048 | 0.2706 | 6.5257 | 2.08x |
| `ddim_3` | 24 | 11.6579 | 0.3438 | 0.0124 | 0.3062 | 6.6224 | 3.43x |
| `ddim_2` | 24 | 8.2588 | 0.2779 | 0.0210 | 0.3772 | 6.6471 | 4.84x |
| `ddim_1` | 24 | 4.5092 | 0.1427 | 3.5168 | 4.7357 | 9.2789 | 8.87x |

1. 实验设计分析：DDIM 实验的核心变量是采样步数。设计这个参数变化的目的，是验证“减少扩散去噪步数”是否能在显著降低时延的同时，仍保持 waypoint 轨迹的可用性。因为 NoMaD 部署瓶颈首先来自扩散采样，若步数下降后质量损失很小，那么它就是最直接的实时化手段。
2. 结果维度分析：从 `ddpm_10` 到 `ddim_5/3/2`，延迟几乎单调下降，分别获得 2.08x、3.43x、4.84x 加速；这说明采样步数确实是主要时延来源。与此同时，`ddim_5`、`ddim_3`、`ddim_2` 的 `forward_progress_mean` 分别为 6.5257、6.6224、6.6471，并没有因为提速而明显恶化，反而略高于 `ddpm_10` 的 6.4998。真正的问题出现在 `ddim_1`：虽然延迟只有 4.5092 ms，但 `mse_vs_baseline_mean` 暴涨到 3.5168，`diversity` 也异常升到 4.7357，说明其采样轨迹已经明显偏离基线分布，不能再视为“同类轨迹的快速近似”。
3. 结论：就正式论文结论而言，`ddim_2` 是当前最优部署配置，因为它在 24 个 case 上实现了 4.84x 加速，同时仍维持与基线相近的路径长度和前进能力；`ddim_5` 可以作为更保守的稳健备选；`ddim_1` 不应作为最终推荐，只能写成极限加速参考点。

| 0.5 | 24 | 78.2698 | 0.0160 | 0.2850 | 8.5146 | 2.8750 | 0.1137 |
| 1.0 | 24 | 79.7498 | 0.0476 | 0.2774 | 8.5725 | 2.9013 | 0.1143 |
| 2.0 | 24 | 78.8074 | 0.1438 | 0.2990 | 8.5273 | 2.9518 | 0.1217 |
| 4.0 | 24 | 78.9217 | 0.5133 | 0.3041 | 8.4831 | 3.0886 | 0.1343 |

1. 实验设计分析：CFG 实验的核心变量是 guidance scale。设计这个参数变化，是为了验证“在 NoMaD 条件分布上施加更强目标引导”是否能让轨迹更集中、更贴近目标，同时避免出现过度牵引、横向偏移放大或推理代价过高的问题。
2. 结果维度分析：首先，`w>0` 后延迟几乎从约 42.65 ms 翻倍到 78~80 ms，说明 CFG 在当前实现下有明显额外推理代价，因此它不能默认常开。其次，`forward_progress_mean` 在 `w=1.0` 时达到 8.5725，是所有配置中最高，说明适度引导确实可以提升朝目标推进的能力；但当 `w` 提高到 2.0 和 4.0 时，`lateral_abs_mean` 从 2.8855 上升到 2.9518 和 3.0886，`shift_vs_w0_mean` 也从 0.0476 上升到 0.1438 和 0.5133，表明轨迹已经开始偏离无引导基线，出现“引导过强导致轨迹形状失真”的趋势。
3. 结论：`w=0.0` 仍应作为整体默认配置，因为它成本最低且结果稳定；`w=1.0` 适合写成障碍场景增强选项，因为它在正式统计结果中拥有最高的前进能力；`w>=2.0` 不适合作为通用配置，`w=4.0` 更应明确标注为过度引导示例，而不是候选最优方案。

### 需要形成的统一结论

1. 哪个 DDIM 步数最适合作为部署版本。
2. 哪个 CFG 引导强度最适合目标导航。
3. 哪些配置可以直接迁移到 Lite3/Tron1 的 MuJoCo 和真机工作中。
4. 哪些结论在多个测试套件和多次重复运行后依然稳定成立。

### 联合优化结果分析

1. 实验设计分析：联合实验的目的，不是重复前面的 DDIM 或 CFG 单因素结论，而是检验两者是否存在耦合效应。因为单独看 DDIM 可能得到“步数越少越快”，单独看 CFG 可能得到“`w=1.0` 更有引导性”，但真正部署时要同时满足实时性、前进能力、轨迹平滑性和横向稳定性，所以必须做联合网格搜索。
2. 结果维度分析：完整 20 组结果表明，所有 Top-5 配置都来自 DDIM 而不是 DDPM，说明部署端的最优区域已经明确转移到了 DDIM。`ddim2_w0.0` 之所以排第一，不是因为它在某一项上极端最优，而是因为它在延迟、前进距离、多样性和平滑度之间取得了最均衡的综合表现。虽然 `ddim2_w1.0` 和 `ddim2_w0.5` 在前进距离上略高，但它们的时延上升明显，综合评分反而低于无 CFG 版本，这说明 CFG 的收益是场景相关的，而不是全局普适的。
3. 结论：论文中的统一推荐配置应改为 `DDIM-2 + w=0.0`，这是真正由联合优化支持的全局最优解；`CFG w=1.0` 不能再写成默认最优，而应写成“在障碍更密集场景中的增强备选”，这个结论后面会由 Lite3 MuJoCo 的 medium 地图结果进一步支撑。

### 你要整理出的链路

4. 状态机：`idle / standup / navigate / explore / recovery_back / recovery_turn / completed / failed`。
5. 结果管理：topomap、mission queue、日志、FPV 保存与恢复统计。

### 状态机全流程检查结论

当前 Lite3 MuJoCo 状态机已经具备完整的闭环执行链，具体流程可以写成下表：

| 状态 | 触发条件 | 主要动作 | 下一状态 |
|---|---|---|---|
| `idle` | 系统启动 | 等待进入任务执行 | `standup` |
| `standup` | `idle` 后自动进入 | 机器人站立、底层姿态稳定 | `navigate` / `explore` / `walk` |
| `navigate` | 导航模式或 mission 模式 | 读取当前观测、匹配 topomap、生成 waypoint、执行局部导航 | `navigate` / `recovery_back` / `completed` / `failed` |
| `explore` | 探索模式 | 使用 `goal mask = 1` 进行无目标局部探索 | `explore` / `recovery_back` / `completed` / `failed` |
| `walk` | 纯运动测试模式 | 直接执行保守前进指令，验证低层 locomotion | `walk` / `completed` / `failed` |
| `recovery_back` | 卡住检测触发 | 保守后退，尝试脱离局部死锁 | `recovery_turn` / `completed` / `failed` |
| `recovery_turn` | 后退恢复结束 | 原地转向并清空 stuck 标记 | `navigate` / `explore` / `completed` / `failed` |
| `completed` | 到达目标、mission 完成、探索/步数到上限 | 触发安全停车并写入结果 | 终止 |
| `failed` | 机器人跌倒、窗口关闭、桥接失败等 | 触发安全停车并写入失败结果 | 终止 |

从完整性检查角度看，当前状态机已经覆盖了仿真部署所需的关键闭环：启动、站立、局部导航、无目标探索、卡住恢复、任务完成、失败退出和结果保存。并且这一轮代码补充后，`completed` 和 `failed` 两个终止状态都会显式触发 `safe_stop`，`recovery_back`、`recovery_turn`、`walk` 也会复用统一的失败检查，因此状态机不再只是“能跑”，而是具备了更完整的安全收口逻辑。

不过还要明确边界：`generate-topomap` 和随机生成起终点这两类流程依赖 MuJoCo 环境对象，因此目前只属于仿真后端能力；真机部署时，topomap 应来自离线采集或现场预构建目录，而不是在线随机生成。

### 状态机完整性结论

1. 对 MuJoCo 仿真而言，这套状态机已经是完整可运行的 NoMaD 部署闭环。
2. 对真机部署而言，状态机本体已经够用，但还需要在它上面增加一个“导航主机”来负责任务切换、后端接入和安全管理。

## 7.5 第十三步：补探索模式与纯运动模式

### 探索模式

```bash
python scripts/simulation/nomad_mujoco_lite3_nav.py --mode walk-test
python scripts/simulation/nomad_mujoco_lite3_state_machine.py --mode walk-test
```

探索模式这一节建议在教程里直接写明原理，而不要只写成“没有目标也能跑”。  
训练阶段 `goal_mask_prob = 0.5` 的作用，本质上是让模型同时学习两类分布：有目标时的 `p(a | o, g)`，以及遮蔽目标时的 `p(a | o)`。  
因此，部署时把 `mask` 设为 `1`，并不是让模型“瞎走”，而是调用它在训练中学到的局部可通行先验，让它根据当前图像和历史上下文生成一组合理的短时 waypoint 轨迹。

这里还要避免另一个常见误解：探索模式不是对视野中的所有空位做几何枚举，也不是显式 frontier search。  
更准确地说，它是从当前观测条件下采样若干条可能轨迹；如果前方只有一条明显通路，轨迹会更集中，如果前方有多个可行方向，采样结果才可能体现出一定多样性。

### 这两步的作用

1. 探索模式用于说明 NoMaD 不只支持目标导航，还支持无目标探索。
2. 纯运动测试用于证明低层 locomotion policy 本身可运行。

### 注意事项

1. 评估探索模式时，不要只截图最终执行的单个 waypoint，最好同时保存多条采样轨迹，这样更容易说明模型学到的是“局部探索分布”而不是单一路径。
2. 如果探索结果总是过于保守或总朝单一方向前进，优先检查训练数据分布和采样数量，而不是直接下结论说 `goal mask` 失效。

### 当前已有结果与分析

结果文件：

1. `results/nomad_mujoco/20260410_144106_explore_mujoco/summary.txt`
2. `results/nomad_mujoco/20260410_144120_walk_test/summary.txt`

| 模式 | 步数 | 总距离(m) | 结果说明 |
|---|---:|---:|---|
| 探索模式 | 100 | 7.763 | 在无目标条件下持续输出局部探索轨迹 |
| 纯运动测试 | 48 | 7.094 | 低层 locomotion 可稳定推进 |

1. 实验设计分析：探索模式和纯运动测试的设计目的不同。探索模式是为了验证 `goal mask` 机制是否真的让模型学会了 `p(a|o)` 这一类“无目标条件下的局部可通行先验”；纯运动测试则是为了把高层导航和低层运动控制解耦，确认即使不依赖复杂导航逻辑，底层 locomotion 依然能稳定工作。
2. 结果维度分析：探索模式在 100 步内累计覆盖 7.763 m，说明系统并没有在探索状态下原地抖动或完全失去前进能力，而是在持续输出可执行的短时 waypoint；纯运动测试在 48 步下前进 7.094 m，则说明低层 locomotion 和 MuJoCo 物理执行链路是通的，这一点很重要，因为如果纯运动都不稳定，那么导航模式的异常就不能直接归因于 NoMaD。
3. 结论：探索模式结果可以作为论文中“系统同时支持目标导航与无目标探索”的证据；纯运动测试结果则可以作为第五章中层 PD 和底层运控链路有效的独立佐证。

### 推荐的真机部署状态机

对于真机，不建议把 `navigate.py` 和 `explore.py` 仅仅理解成两个分散脚本。  
更适合论文表达、也更适合实际运行的方案，是把它们封装成同一套部署状态机：

1. `idle`：等待任务、等待人工确认、等待模式切换。
2. `navigate`：执行 `mask = 0` 的目标导航。
3. `explore`：执行 `mask = 1` 的局部探索。
4. `recovery`：处理卡住、偏航、局部碰撞风险、观测异常。
5. `estop`：人工或安全逻辑触发的紧急停机。

当前仓库已经给出了 `navigate` 和 `explore` 两类入口，因此从工程实现角度看，这个状态机是完全可以搭出来的；论文里也建议直接把系统写成“可切换导航/探索模式的统一部署框架”。

### 导航主机设计思路

仅有状态机还不够，因为状态机解决的是“单次闭环执行”，而不是“整机任务编排”。更适合写进论文和落到工程里的方案，是在状态机之上再加一层导航主机：

1. 导航主机：负责选择后端、装载任务、切换模式、启动或停止状态机。
2. 状态机执行层：负责单次任务内的 NoMaD 推理、PD 桥接、底层控制和恢复逻辑。

这层主机已经在仓库中落成到 [nomad_navigation_host.py](../scripts/deployment/nomad_navigation_host.py)，其职责可以概括为：

| 主机职责 | 具体内容 |
|---|---|
| 后端接入 | 选择 `mujoco` 或 `real` 后端；MuJoCo 直接运行，真机通过 Python bridge 适配器接入 |
| 任务编排 | 读取单任务参数或任务计划文件，按顺序派发 `navigate`、`mission`、`explore`、`walk-test` |
| 状态机调度 | 为每个任务实例化状态机执行链，把任务配置传给 `Lite3System` |
| 模式切换 | 在局部导航和多目标 mission 之间切换，而不是把两者写成两套完全独立程序 |
| 结果管理 | 保存主机任务计划、执行摘要，并让状态机继续输出底层运行日志 |

这里要特别区分两个层次的“切换”：

1. 状态机内部切换：例如 `navigate -> recovery_back -> recovery_turn -> navigate`，这是执行期的闭环恢复。
2. 导航主机切换：例如 `navigate task -> mission task`，这是任务级调度。

从论文表述上说，导航主机不是替代状态机，而是位于状态机之上的“任务编排层”。这样写以后，你的系统结构就会更清晰：高层 NoMaD 与状态机负责自治执行，导航主机负责调度与平台接入。

### 导航主机的 MuJoCo / 真机双后端设计

当前导航主机支持两种接入方式：

1. `mujoco` 后端：直接调用 Lite3 MuJoCo 状态机，适合仿真验证和任务计划联调。
2. `real` 后端：通过 `ExternalBridgePlatform` 适配 Python bridge，要求真机桥接模块提供相机、速度命令、位姿、速度、停车等接口。

这意味着导航主机本身不关心底层是 MuJoCo 还是 ROS/SDK 真机，只关心后端是否满足统一平台接口。也正因为如此，它可以把同一套 NoMaD + 状态机逻辑同时复用于仿真和真机。

### 导航主机的推荐使用方式

单任务模式：

```bash
python scripts/deployment/nomad_navigation_host.py \
  --backend mujoco \
  --mode navigate --map easy --topomap-dir topomaps/easy
```

任务计划模式：

```bash
python scripts/deployment/nomad_navigation_host.py \
  --backend mujoco \
  --plan-file scripts/configs/navigation_host/lite3_navigation_host_plan.json
```

真机桥接模式：

```bash
python scripts/deployment/nomad_navigation_host.py \
  --backend real \
  --bridge-module my_robot_bridge.module \
  --bridge-class Lite3RobotBridge \
  --plan-file scripts/configs/navigation_host/lite3_navigation_host_plan.json
```

### 导航主机设计结论

1. MuJoCo 仿真中的 Lite3 NoMaD 状态机部署已经存在，并且可以直接作为导航主机的执行后端。
2. 导航主机应被写成“状态机上层的统一任务编排器”，而不是另一个零散脚本。
3. 论文里可以把它作为仿真到真机迁移的关键工程层：同一套任务计划和状态机执行逻辑，通过不同后端适配器接入 MuJoCo 和真机。

### 导航模式建议设计成两层目标管理

如果你希望系统支持“多个目标”，建议在教程和论文中区分两层含义：

1. 局部层：一个 topomap 内部的多个节点。  
   这一层当前代码已经支持。系统会在局部窗口内根据距离预测选择当前子目标节点，再逐步推进到 `goal_node`。

2. 任务层：多个高层目标组成的 mission queue。  
   例如 `Goal A -> Goal B -> Goal C`。这一层建议单独做一个任务管理器：当前 topomap 或目标节点完成后，再切换到下一项任务。

这里的表述要尽量准确：距离预测网络主要负责“当前激活候选集合内的局部子目标选择”，不要把它写成“直接完成全局多目标排序”。  
如果后面真的要做“最近目标优先”，最好明确说明这是你额外设计的调度策略，而不是原始 NoMaD 部署脚本自带的全局规划器。

### 注意事项

1. 先保留低速保守参数，不要一开始给高速度。
2. 先在遥操作与静态感知条件下确认相机图像正确，再进入 NoMaD 自主阶段。

## 9.3 第二十一步：按四个层次推进 Lite3 真机测试

### 探索模式的额外工程约束

如果系统长期停留在 `explore` 模式，并且没有退出条件，那么平台会持续根据当前观测重新生成局部 waypoint，并持续移动。  
这不等于纯随机乱走，但在工程上仍然可能表现为局部徘徊、回环、或在有限区域内反复试探。

因此，真机部署时建议至少加入以下限制：

1. 固定探索时间预算或里程预算。
2. 回环检测或重复区域检测。
3. 卡住检测与自动切换 `recovery`。
4. 人工接管和急停开关。
5. 当找到目标、收到新任务或风险升高时，自动退出 `explore`。

### 注意事项

1. 每一层通过后再进入下一层。
2. 不要跳层。

## 13. 常见错误与规避方法

### 错误一：继续把 Lite3 写成“未来工作”

规避方法：

1. 直接以 [nomad_mujoco_lite3_nav.py](../scripts/simulation/nomad_mujoco_lite3_nav.py) 和 [nomad_mujoco_lite3_state_machine.py](../scripts/simulation/nomad_mujoco_lite3_state_machine.py) 为证据，把它们写进第五章主体。

### 错误二：Tron1 一上来就想全做完

规避方法：

1. 先跑 [nomad_mujoco_tron1_nav.py](../scripts/simulation/nomad_mujoco_tron1_nav.py) 固化资产与阶段计划。
2. 先做可运行版本，再补复杂场景。

### 错误三：真机部署前跳过静态感知检查

规避方法：

1. 先相机、再桥接、再低速、再导航。

### 错误四：把平台差异写得太虚

规避方法：

1. 明确写出 Lite3 和 Tron1 在桥接层、低层控制器和安全约束上的区别。

### 错误五：所有结果堆在一起没有证据链

规避方法：

1. 每个实验都保留结果目录。
2. 每个章节都建立脚本到图表的索引。

### 错误六：统计实验仍然只跑单次

规避方法：

1. DDIM 和 CFG 的正式结论统一使用统计版脚本。
2. 至少保留平均值、标准差和置信区间。

### 错误七：视觉编码器升级只比 DINOv2 和原始基线

规避方法：

1. 至少增加一种额外编码器作为补充对比。
2. 统一使用 [encoder_comparison_experiment.py](../scripts/experiments/encoder_comparison_experiment.py) 做评测。
