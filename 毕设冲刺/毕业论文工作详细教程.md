# 基于 NoMaD 的毕业论文工作详细教程

> 文档用途：指导你把当前仓库中的已有成果，整理成一套可执行、可复现、可展示的毕业论文主体工作流程。  
> 适用范围：项目运行环境为 Ubuntu 20.04，训练环境为 Ubuntu 22.04，文中统一使用相对路径。  
> 使用原则：先固化基线，再做优化，再做足式系统设计，最后做材料整合，不要一开始就分散精力。

---

## 1. 教程目标

这份教程不是教你“怎么写论文文字”，而是教你“怎么把论文主体工作一步一步做完整”。  
最终你需要得到四类成果：

1. 可复现的 NoMaD 基线结果。
2. 可量化的优化实验结果。
3. 面向足式机器人的系统设计与可行性验证结果。
4. 可直接支撑论文三章主体内容的图、表、日志和结论。

---

## 2. 当前项目的真实起点

开始之前，先明确你现在不是从零开始，而是在已有成果上继续推进。根据当前仓库内容，你已经具备：

1. 基线脚本：`scripts/check_dataset.py`、`scripts/offline_inference.py`
2. 优化脚本：`scripts/ddim_experiment.py`、`scripts/cfg_experiment.py`
3. DINOv2 探索脚本：`scripts/nomad_vint_dinov2.py`、`scripts/train_dinov2.py`
4. 足式仿真脚本：`scripts/lite3_sim.py`
5. 已有结果目录：`results/day1/`、`results/day2/`、`results/day3/`
6. 已有工作量方案：`毕设冲刺/毕业论文工作量设计方案.md`

同时也有一个必须优先处理的问题：

1. 多个脚本存在绝对路径硬编码，不能直接满足 Ubuntu 20.04/22.04 双环境部署要求。

所以你的正确推进顺序不是“继续加实验”，而是：

1. 固化项目环境和路径。
2. 复核基线。
3. 补齐优化实验。
4. 完成足式系统设计和可行性验证。
5. 整理成论文主体工作材料。

---

## 3. 本教程配套脚本

为了让流程更可执行，这次新增了 3 个辅助脚本。教程中会直接用到它们，但不在文档里展示脚本内容。

1. 环境检查脚本：[env_check.py](../scripts/env_check.py)
2. 路径审计脚本：[path_audit.py](../scripts/path_audit.py)
3. 结果汇总脚本：[thesis_result_summary.py](../scripts/thesis_result_summary.py)

它们的作用分别是：

1. 检查仓库结构、数据集、权重、结果目录是否齐全。
2. 扫描仓库中的绝对路径和平台耦合字符串。
3. 自动提取当前 `results/` 中的基线、DDIM、CFG 关键结果，生成论文表格草稿。

## 4. 总体执行顺序

建议严格按下面顺序做，不要跳步：

1. 阶段一：环境和路径固化
2. 阶段二：NoMaD 基线复现与整理
3. 阶段三：优化实验补齐
4. 阶段四：足式系统分析与验证
5. 阶段五：材料整合与工作量封装

如果时间紧张，优先级也按这个顺序执行。

## 5. 阶段一：环境和路径固化

这一阶段的目标是把项目变成“能稳定跑”的状态。  
如果这一步不做好，后面任何结果都很难稳定复现。

### 5.1 第一步：建立双环境边界

#### 操作目标

把训练和部署彻底分开，避免环境污染。

#### 具体操作

1. 在 Ubuntu 22.04 机器上准备训练环境。
2. 在 Ubuntu 20.04 机器上准备部署环境。
3. 两边都使用同一份项目代码目录结构，但不要混用中间产物。
4. 训练侧只负责：
   - 训练
   - 离线实验
   - 结果生成
5. 部署侧只负责：
   - 推理
   - 控制对接
   - 足式平台验证

#### 推荐命令

训练环境：

```bash
conda create -n nomad-thesis python=3.8 -y
conda activate nomad-thesis
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

部署环境：

```bash
conda create -n nomad-deploy python=3.8 -y
conda activate nomad-deploy
pip install --upgrade pip
pip install -r scripts/requirements.txt
cd train
pip install -e .
cd ..
```

#### 注意事项

1. 不要在 Ubuntu 20.04 上承担训练任务。
2. 不要把 Ubuntu 22.04 训练日志目录直接当成部署目录使用。
3. 权重文件和配置文件可以同步，日志目录不要混用。
4. 如果 ROS 依赖只在 Ubuntu 20.04 可用，就把 ROS 相关验证严格留在部署环境。

### 5.2 第二步：先跑一次环境检查

#### 操作目标

确认仓库结构、数据集、结果目录、权重文件是否满足后续实验条件。

#### 具体操作

在项目根目录运行：

```bash
python scripts/env_check.py --save
```

#### 产出

1. 终端检查结果
2. 自动保存的检查报告，位置在 `results/tools/`

#### 你需要重点看什么

1. `dataset_root` 是否存在。
2. `trajectory_count` 是否正常。
3. `model_weights` 是否存在。
4. `train/config/nomad.yaml` 和 `deployment/config/models.yaml` 是否存在。

#### 注意事项

1. 如果 `model_weights` 缺失，不要继续跑基线推理，先补齐权重。
2. 如果 `torch` 导入失败，说明当前环境只是“代码目录可见”，不是“实验环境可用”。
3. 报告里要保留一份，后续可以作为论文中的“实验环境准备证明材料”。

### 5.3 第三步：做绝对路径排查

#### 操作目标

找出所有影响跨平台运行的绝对路径。

#### 具体操作

在项目根目录运行：

```bash
python scripts/path_audit.py --save
```

#### 产出

1. 路径审计结果
2. 自动保存的报告，位置在 `results/tools/`

#### 你要如何使用这个结果

1. 先优先处理 `scripts/` 下的实验脚本。
2. 再处理 `train/config/nomad_dinov2.yaml` 中的数据路径。
3. 文档类文件里的历史绝对路径可以暂时不改，但论文最终引用时要统一改成相对路径表述。

#### 注意事项

1. 你当前最关键的不是“把全仓库所有历史文档都修完”，而是先保证实验链路能跑。
2. 优先级最高的是这些脚本：
   - `scripts/offline_inference.py`
   - `scripts/ddim_experiment.py`
   - `scripts/cfg_experiment.py`
   - `scripts/train_dinov2.py`
   - `scripts/lite3_sim.py`
3. 改路径时要统一策略：
   - 根目录通过脚本文件位置推导
   - 数据路径和权重路径通过相对路径或配置文件读取
4. 不要一部分脚本走相对路径，一部分脚本继续写死固定根目录。

### 5.4 第四步：完成路径重构

#### 操作目标

把当前项目改造成可在 Ubuntu 20.04 和 Ubuntu 22.04 之间迁移的形式。

#### 具体操作

1. 打开上一步生成的路径审计报告。
2. 按优先级逐个处理实验脚本中的固定根目录写法。
3. 统一改为通过脚本位置推导仓库根目录。
4. 对训练配置文件中的数据路径，改成你当前机器上的相对或可迁移配置写法。
5. 修改完成后，再重新运行一次：

```bash
python scripts/path_audit.py --save
```

#### 判断标准

1. 关键实验脚本不再依赖固定用户名和固定目录。
2. 同一份代码在不同 Ubuntu 环境中只需要改少量配置，不需要重新改脚本。

#### 注意事项

1. 这一步本身就是论文里的工程性工作量，不是“杂活”。
2. 后面论文第三章里可以明确写成“系统重构与可复现性增强”。

---

## 6. 阶段二：NoMaD 基线复现与整理

这一阶段的目标是完成论文第三章的核心支撑材料。  
你要证明：当前 NoMaD 基线在你的数据集和代码链路下是可信的。

### 6.1 第五步：检查 GoStanford 数据集

#### 操作目标

确认数据集结构、轨迹目录、图像与 `traj_data.pkl` 的对应关系没有问题。

#### 具体操作

```bash
python scripts/check_dataset.py
```

#### 你要记录的内容

1. 数据集总轨迹数。
2. 抽查轨迹是否能正确读取。
3. 是否有损坏样本。

#### 产出

1. 数据集检查日志
2. 论文可用的“数据集接入正确性”结论

#### 注意事项

1. 如果数据集读取异常，不要直接继续做优化实验。
2. 数据集检查结果要与论文中的数据规模表述保持一致。

### 6.2 第六步：跑离线基线推理

#### 操作目标

复现 NoMaD 的离线推理结果，形成论文中的基线图和基线指标。

#### 具体操作

```bash
python scripts/offline_inference.py
```

#### 你要看哪些输出

1. 推理耗时
2. 推理频率
3. 预测距离
4. 轨迹可视化图
5. `summary.txt`

#### 对应结果目录

1. `results/day1/..._offline_inference/`

#### 你要做的整理动作

1. 记录模型参数量。
2. 记录 DDPM 10 步采样耗时。
3. 保存两张图：
   - 导航模式轨迹图
   - 探索模式轨迹图
4. 把 `summary.txt` 中的关键数值抄到自己的实验总表。

#### 注意事项

1. 这里的重点不是只跑通，而是要保留证据链。
2. 每次运行后不要覆盖旧结果，保留时间戳目录。
3. 后面论文里的基线结论要以这里的 `summary.txt` 为准。

### 6.3 第七步：自动汇总当前已有结果

#### 操作目标

把当前已有的 `results/` 自动整理成论文草表，避免手工抄错数值。

#### 具体操作

```bash
python scripts/thesis_result_summary.py --save
```

#### 产出

1. 一份 Markdown 汇总，位置在 `results/summary/`

#### 这一步的用途

1. 直接给论文中的实验表格提供草稿。
2. 校验基线、DDIM、CFG 三部分数值是否一致。

#### 注意事项

1. 每次做完一个新实验，都建议重新运行一次。
2. 这份表是“汇总草稿”，最终论文表格还要补充方法说明和结论列。

## 7. 阶段三：优化实验补齐

这一阶段对应论文第四章。  
原则是只做对论文主线最有价值的优化，不要无限扩展。

### 7.1 第八步：完成 DDIM 加速实验

#### 操作目标

验证扩散采样加速后，NoMaD 是否能在速度和轨迹质量之间取得更好的部署平衡。

#### 具体操作

```bash
python scripts/ddim_experiment.py
```

#### 你要提取的指标

1. 每种配置的平均推理时间
2. 时间标准差
3. 相对基线的 MSE
4. Diversity
5. Speedup

#### 你要形成的结论格式

1. 哪个步数配置速度最快。
2. 哪个步数配置速度与质量折中最好。
3. 你最终推荐哪个配置用于部署。

#### 当前建议

结合已有结果，优先把 `DDIM-5` 作为论文中的推荐配置候选。

#### 注意事项

1. 不要只强调速度，不看质量偏差。
2. `DDIM-1` 即使加速最大，也不一定适合正式部署结论。
3. 图和表必须成对出现：
   - 时间对比图
   - 质量偏差图
   - 推荐结论表

### 7.2 第九步：完成 CFG 引导实验

#### 操作目标

验证不同引导强度下，NoMaD 的目标导向能力、多样性和推理开销之间的关系。

#### 具体操作

```bash
python scripts/cfg_experiment.py
```

#### 你要提取的指标

1. `w` 不同取值下的 Diversity
2. Mean Displacement
3. Inference Time
4. 各 `w` 值对应轨迹图

#### 你要形成的结论格式

1. `w=-1` 对应探索模式。
2. `w=0` 对应标准条件生成。
3. `w>0` 对应目标引导增强。
4. 最后给出一个推荐引导强度。

#### 当前建议

结合已有结果，优先把 `w=1.0` 作为正式论文中的推荐配置候选。

#### 注意事项

1. 这里不要只说“效果更好”，要明确说是“更强的目标导向”还是“更低的多样性”。
2. CFG 增加推理时间是正常现象，要把这个代价写清楚。

### 7.3 第十步：推进 DINOv2 编码器实验

#### 操作目标

验证更强视觉表征是否能提升跨场景、跨视角或跨形态的视觉编码质量。

#### 具体操作

先检查配置文件中的数据路径是否已经改好，再运行：

```bash
cd train
python ../scripts/train_dinov2.py -c config/nomad_dinov2.yaml
cd ..
```

#### 你要记录的内容

1. 训练是否稳定。
2. 损失曲线是否正常。
3. 最终权重是否导出。
4. 与原始编码器相比，是否有明确的量化提升。

#### 如果训练完成，还要做什么

1. 用统一的离线推理方式做对比。
2. 尽量与基线在同一评估设置下比较。
3. 记录速度变化和精度变化。

#### 你要怎样决定它在论文中的位置

1. 如果结果明显提升，就作为第四章的核心增强方法之一。
2. 如果结果不稳定或提升有限，就把它定位成“重要探索项”，不要强行写成主结论。

#### 注意事项

1. 当前仓库中的 `train/config/nomad_dinov2.yaml` 存在路径耦合风险，这一步必须建立在阶段一完成之后。
2. 不要让 DINOv2 训练拖慢整个毕设主线。
3. 时间不够时，优先保住 DDIM 和 CFG 的完整性，再决定是否把 DINOv2 升级为核心结果。

### 7.4 第十一步：生成优化实验总表

#### 操作目标

把 DDIM、CFG、DINOv2 三类实验统一进一套结果框架。

#### 具体操作

1. 重新运行一次：

```bash
python scripts/thesis_result_summary.py --save
```

2. 手工补充 DINOv2 的结果项。
3. 整理成一张总表，列建议如下：
   - Method
   - Real-time
   - Goal Guidance
   - Visual Generalization
   - Inference Time
   - Main Conclusion

#### 注意事项

1. 不要把不同实验的评价标准混在一起。
2. 所有对比都要明确“是在什么条件下比较的”。

## 8. 阶段四：足式系统分析与验证

这一阶段对应论文第五章。  
这部分的重点不是“做一个完整足式产品”，而是回答三个问题：

1. 为什么 NoMaD 可以从轮式迁移到足式。
2. 迁移时系统实现上哪里不一样。
3. 你的系统设计方案是否合理、可行。

### 8.1 第十二步：先做系统级分析，不要先陷入仿真细节

#### 操作目标

先把论文最核心的系统逻辑讲清楚。

#### 具体操作

你需要基于这几部分代码，手工梳理系统链路：

1. `deployment/src/navigate.py`
2. `deployment/src/pd_controller.py`
3. `deployment/src/utils.py`
4. `scripts/lite3_sim.py`

#### 你要整理出的系统链路

1. 图像观测输入
2. NoMaD 输出 waypoint
3. waypoint 转速度指令
4. 速度指令进入平台控制层
5. 轮式平台直接执行
6. 足式平台需要中间动作接口层再交给步态控制器

#### 你要形成的核心表述

1. 轮式平台中，高层速度命令可直接被底盘执行。
2. 足式平台中，高层导航输出必须经过动作接口层和步态控制层。
3. 因此，NoMaD 的跨形态迁移不是简单换底盘，而是系统重构问题。

#### 注意事项

1. 这一段是论文和答辩里最关键的解释逻辑。
2. 就算仿真结果不完美，这一层系统分析也必须完整。

### 8.2 第十三步：设计轮式到足式的接口方案

#### 操作目标

把“理论上可迁移”变成“工程上怎么迁移”。

#### 具体操作

你要明确设计以下 5 层结构：

1. 数据与配置层
2. 模型推理层
3. 动作接口层
4. 平台执行层
5. 反馈评估层

#### 你要写清楚的内容

1. 哪一层是轮式和足式共享的。
2. 哪一层是迁移时新增的。
3. 哪些安全约束只在足式平台下需要特别强调。

#### 足式系统中建议强调的约束

1. 最大线速度约束
2. 最大角速度约束
3. waypoint 曲率约束
4. 低速保守模式

#### 注意事项

1. 这一部分最好配一张系统框图。
2. 你可以不直接在文档里画图，但一定要把图的结构先整理出来。

### 8.3 第十四步：跑足式或轮足对比仿真

#### 操作目标

给系统设计提供最基本的验证证据。

#### 具体操作

如果 PyBullet 环境可用，运行：

```bash
python scripts/lite3_sim.py --compare
```

#### 你要观察的内容

1. waypoint 到速度命令的转换是否合理。
2. 轮式和足式在同一路径下的跟踪差异。
3. 足式系统是否需要更保守的约束设置。

#### 如果仿真条件不完善，怎么处理

1. 至少完成接口级验证。
2. 至少完成轮式和足式控制链差异分析。
3. 至少给出速度约束和动作接口方案。

#### 注意事项

1. 不要把这一步的目标定成“做出高度完整的足式闭环产品”。
2. 你的论文重点是“系统适配和可行性论证”，不是“完整商业级控制器实现”。

### 8.4 第十五步：决定 gait shake 实验是否纳入主体

#### 操作目标

避免在毕业阶段被非核心实验拖住。

#### 判断规则

1. 如果你已经把基线、DDIM、CFG、足式系统设计都做完整了，再考虑补 gait shake。
2. 如果时间紧张，就把 gait shake 降级为补充实验或展望，不要影响主线。

#### 注意事项

1. 你现在的主线已经足够形成完整工作量。
2. gait shake 不是必须项，不要让它反过来破坏整体结构。

## 9. 阶段五：材料整合与工作量封装

这一阶段的目标是把所有实验变成“论文主体工作材料”，而不是散落的脚本和图片。

### 9.1 第十六步：按论文三章整理材料

#### 第三章材料

你需要准备：

1. 数据集说明
2. NoMaD 基线流程图
3. 基线推理结果
4. 项目路径重构与系统重构说明

#### 第四章材料

你需要准备：

1. DDIM 对比图和结论
2. CFG 对比图和结论
3. DINOv2 结果与定位
4. 最终推荐部署配置

#### 第五章材料

你需要准备：

1. 轮式到足式的系统结构图
2. waypoint 到速度接口说明
3. 足式安全约束设计
4. 仿真或接口级可行性验证结果

### 9.2 第十七步：建立实验证据索引

#### 操作目标

保证论文里每个结论都能追溯到图、表、日志或脚本。

#### 推荐做法

建立一个你自己的实验索引表，至少包含：

1. Experiment Name
2. Script Path
3. Result Path
4. Figure Path
5. Core Metric
6. Chapter Usage
7. Final Conclusion

#### 注意事项

1. 以后写论文时，所有结论都从这个索引表找来源。
2. 不要凭记忆填论文数据。

### 9.3 第十八步：确定最终推荐配置

#### 操作目标

给整篇论文一个明确落点。

#### 当前推荐策略

如果后续实验没有推翻现有趋势，建议把最终推荐配置定为：

1. NoMaD
2. DDIM-5
3. CFG `w=1.0`
4. 完成相对路径与配置重构

#### DINOv2 的处理建议

1. 如果结果显著提升，就纳入推荐配置。
2. 如果结果不稳定，就保留为增强探索项。

#### 注意事项

1. 推荐配置必须是你能解释清楚的，不是参数最多的那个。
2. 推荐配置的依据必须来自你的实验，不要只凭主观判断。

## 11. 你每天的推荐执行方式

为了避免推进混乱，建议你每天按下面节奏做：

### 上午

1. 先跑检查脚本确认环境状态。
2. 只推进一个核心实验或一个核心系统任务。

### 下午

1. 整理结果图和日志。
2. 更新实验索引表。
3. 记录当天结论，不要只保存图不写结论。

### 晚上

1. 重新检查今天的结果是否真的能支撑论文。
2. 判断下一天是继续补实验，还是转入系统设计整理。

## 12. 常见错误与规避方法

### 错误一：一上来继续加新实验

规避方法：

1. 先做环境和路径固化。
2. 先保住基线和已完成实验。

### 错误二：把未完成实验写成既有成果

规避方法：

1. 已完成、进行中、补充项必须分开记录。

### 错误三：把足式迁移理解成“换个底盘”

规避方法：

1. 强调动作接口层和步态控制层的新增需求。

### 错误四：数据和图表来源混乱

规避方法：

1. 每次实验都保留时间戳目录。
2. 每次整理都更新结果汇总和实验索引表。

### 错误五：过度追求 DINOv2 或 gait shake，导致主线失控

规避方法：

1. 先保证基线、DDIM、CFG、系统设计完整。
2. 其余内容按时间作为增强项处理。
